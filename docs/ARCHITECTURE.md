# Architecture

> وضعیت: پارت‌های ۱ تا ۸ منتشر شده‌اند. پارت ۹ به‌صورت محلی پیاده‌سازی شده و منتظر بازبینی کاربر است؛ نتیجه و حدود بررسی در [برنامهٔ اجرا](plans/plans.md) و [راهبرد آزمون](TESTING.md) ثبت شده‌اند. [راهنمای ارزیابی](evaluation-guide.md) سند تکمیلی سنجش کیفیت است؛ نسخه‌های قدیمی مشخصات و طرح فنی در archive فقط برای سابقه نگهداری می‌شوند.

## 1. System Overview

دستیار دانش سازمانی سپهر داده یک برنامهٔ وب فارسی و راست‌به‌چپ برای پرسش از اسناد داخلی است. رابط Next.js از مسیر same-origin درخواست‌ها را به API در FastAPI می‌فرستد. FastAPI هویت و مجوز را بررسی می‌کند، اسناد را در PostgreSQL می‌خواند، بازیابی واژگانی و معنایی را اجرا می‌کند و برای تولید پاسخ مستند از OpenRouter استفاده می‌کند. PostgreSQL 16.15 موجود روی میزبان با pgvector 0.8.6 از طریق پورت 5433 در دسترس است؛ برنامه باید به پایگاه‌دادهٔ مستقل `enterprise_knowledge_copilot` متصل شود.

Embedding محلی با Ollama روی `localhost:11434` و مدل `nomic-embed-text-v2-moe:latest` انجام می‌شود. این مدل بردار 768بعدی تولید می‌کند؛ digest live-check تأییدشدهٔ مدل `ff9c2f10ef5e` در پیکربندی ثبت می‌شود؛ پرسش با پیشوند `search_query:` و متن سند با `search_document:` ارسال می‌شود. OpenRouter rerank اختیاری و به‌طور پیش‌فرض غیرفعال است (`RERANK_ENABLED=false`) و مدل نمونهٔ آن `nvidia/llama-nemotron-rerank-vl-1b-v2:free` است.

## 2. Architecture Pattern

**Pattern:** یکپارچهٔ ماژولار (modular monolith)، با Next.js و FastAPI به‌عنوان دو فرایند برنامه و یک پایگاه‌دادهٔ PostgreSQL. پارت‌های ۵ تا ۹ به‌ترتیب رابط ورود، parser/chunker، embedding، ingestion پایدار، و import corpus به‌همراه رابط مدیریت اولیه را افزوده‌اند. worker ingestion در همان برنامهٔ API اجرا می‌شود و صف یا سرویس جداگانهٔ Redis/Celery وجود ندارد.

**Reason:** مرزهای ماژولی هویت، اسناد، بازیابی و پاسخ روشن می‌مانند، در حالی که اجرای محلی و تراکنش فعال‌سازی نسخه پیچیدگی سرویس‌های توزیع‌شده را ندارد. frontend و API مرز شبکهٔ مشخصی دارند و اتصال به مدل‌ها پشت adapter قرار می‌گیرد.

## 3. Technology Stack

| حوزه | انتخاب پیشنهادی | پیکربندی/مرز |
|---|---|---|
| Frontend | Next.js و TypeScript | رابط فارسی RTL؛ درخواست مرورگر فقط به پراکسی same-origin در Route Handler |
| Backend | FastAPI و Python 3.12 | API و worker ingestion در یک سرویس؛ یک فرایند و یک کار هم‌زمان ingestion در نسخهٔ اول |
| Database | PostgreSQL 16.15 موجود روی میزبان با pgvector | میزبان از پورت 5433؛ پایگاه‌دادهٔ اختصاصی `enterprise_knowledge_copilot` و `enterprise_knowledge_copilot_test` با حساب محدود؛ allowlist در `app/db/url.py` |
| Authentication | نشست تصادفی در کوکی و گذرواژهٔ Argon2id | hash نشست در DB؛ عمر پیشنهادی ۸ ساعت؛ نقش از رکورد کاربر خوانده می‌شود |
| Login throttling | محدودکنندهٔ حافظه‌ای درون‌فرایندی | پنجرهٔ لغزان ۶۰ ثانیه؛ حدود قابل تنظیم؛ ظرفیت کلید محدود و در اشباع fail-closed؛ جزئیات در SECURITY |
| Storage | متن UTF-8 و دادهٔ مشتق‌شده در PostgreSQL | فایل خام پس از parsing نگهداری نمی‌شود؛ فایل‌های DB و محیط محلی وارد Git نمی‌شوند |
| Hosting | اجرای native روی میزبان توسعه | Next.js و FastAPI؛ این طرح برای DB سرویس جدید Compose تعریف نمی‌کند |
| Generation | OpenRouter با مدل قابل تنظیم | مقدار آغازین پیشنهادی `OPENROUTER_MODEL=google/gemini-2.5-flash`؛ نیازمند smoke test پیش از اتکا |
| Embeddings | Ollama محلی | `httpx` وابستگی runtime است؛ `OLLAMA_EMBED_DIGEST` در پیکربندی و ناهم‌خوانی fail-closed |
| Reranking | OpenRouter اختیاری | مدل `nvidia/llama-nemotron-rerank-vl-1b-v2:free`؛ خاموش به‌صورت پیش‌فرض؛ تنها نامزدهای مجاز را می‌گیرد و همان کلید generation را مصرف می‌کند |
| Payments / Email / Analytics | ندارد | خارج از محدودهٔ نسخهٔ اول |

تنظیم اتصال native از `.env` در ریشهٔ مخزن با نام‌های `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` خوانده می‌شود؛ `DATABASE_URL` قرارداد این پروژه نیست. تنظیم generation با `OPENROUTER_API_KEY` و `OPENROUTER_MODEL`، embedding با `EMBEDDING_PROVIDER`, `OLLAMA_BASE_URL`, `OLLAMA_EMBED_MODEL`, `OLLAMA_EMBED_DIGEST`, `EMBEDDING_DIMENSION`, `EMBEDDING_MAX_TOKENS`, `EMBEDDING_TRUNCATE` و rerank با `RERANK_ENABLED`, `RERANK_PROVIDER=openrouter` و `OPENROUTER_RERANK_MODEL` انجام می‌شود؛ rerank از همان `OPENROUTER_BASE_URL` و `OPENROUTER_API_KEY` استفاده می‌کند. مقادیر secret در `.env` محلی یا مدیر اسرار محیط اجرا می‌مانند و فقط نام متغیرهای جایگزین‌شونده در `.env.example` درج می‌شود. پایگاه‌داده‌های اختصاصی و حساب محدود در ۲۰۲۶-۱۰-۰۴ با `apps/api/sql/provision.sql` روی همین سرویس موجود ساخته شدند؛ `pgvector 0.8.6` در هر دو فعال است و schema با migration `0001` اجرا شده است. مقصد اتصال به‌صورت allowlist روی همین دو نام محدود و در `app/db/url.py` پیش از ساخت URL بررسی می‌شود؛ نام/دادهٔ پایگاه‌های دیگر را تغییر ندهید. مجوز در سطح connection قابل محدودسازی نیست چون سرویس موجود مجوزهای عمومی خود را دارد؛ مرز مجوز در لایهٔ application اعمال می‌شود و لغو یا تغییر مجوز در پایگاه‌های قدیمی ممنوع است.

## 4. System Components

### Frontend

مسئولیت‌ها:

- ارائهٔ ورود، گفتگو، نمایش پاسخ و منابع تا سطح بخش، و صفحات فهرست/وضعیت اسناد مدیر.
- نگه‌داشتن تجربهٔ فارسی و RTL و نمایش خطای عمومی قابل اقدام بدون افشای جزئیات داخلی.
- عبور درخواست از Route Handler هم‌مبدأ؛ حذف هدرهای نقش/هویت ساخته‌شده توسط کاربر و کنترل Origin برای درخواست‌های تغییردهنده.
- نمایش فقط پاسخ ساخته‌شده از claims اعتبارسنجی‌شده و امتناع‌های ثابت سمت سرور؛ متن آزاد مدل مستقیماً نمایش داده نمی‌شود.

### Backend

مسئولیت‌ها:

- احراز نشست، بارگذاری نقش جاری، اعمال مجوز در لایهٔ route و service و تولید دامنهٔ اسناد مجاز سمت سرور.
- اعتبارسنجی بارگذاری، ساخت job، پردازش بخش‌ها و قطعه‌ها، embedding، staging و فعال‌سازی اتمی نسخهٔ آماده.
- اجرای BM25 و جست‌وجوی برداری فقط روی مجموعهٔ مجاز همان درخواست، ادغام رتبه با RRF و rerank اختیاری.
- تولید JSON مقید، اعتبارسنجی دقیق ارجاع/نقل‌قول، بررسی دوبارهٔ مجوز و revision پیش از تحویل کامل پاسخ؛ پاسخ stream نمی‌شود.
- ثبت فرادادهٔ اجرای غیرحساس، خطاهای سیاستی و زمان‌ها؛ عدم ثبت متن خام پرسش، پاسخ، prompt یا سند در `request_runs`.

### Database

مسئولیت‌ها:

- نگهداری کاربران، نشست‌ها، سند و revision جاری، jobهای ingestion، بخش‌ها، قطعه‌ها و بردارهای 768بعدی.
- اعمال کلیدهای خارجی، یکتایی و قیود سازگاری revision/section/chunk؛ نگهداری فرادادهٔ مجاز اجرا بدون متن محتوایی.
- اتصال فقط به پایگاه‌دادهٔ allowlistشدهٔ `enterprise_knowledge_copilot` روی PostgreSQL میزبان.

### Provider adapters

Embedding، generation و reranking از رابط‌های مجزا فراخوانی می‌شوند. مدل/endpoint از محیط تنظیم می‌شود؛ خطا یا timeout باعث انتخاب پنهانی provider جایگزین نمی‌شود. adapter embedding باید پیشوندهای جست‌وجوی Nomic را اعمال کند و ابعاد خروجی را 768 اعتبارسنجی کند.

قرارداد API پیشنهادی (همه پشت پراکسی same-origin):

| مسیر | دسترسی و نتیجه |
|---|---|
| `POST /api/auth/login` | عمومی با Origin معتبر؛ ایجاد نشست |
| `POST /api/auth/logout` | ابطال نشست |
| `GET /api/auth/me` | هویت و نقش جاری سروری |
| `POST /api/answers` | کارمند/مدیر؛ پاسخ کامل مستند یا امتناع |
| `GET /api/documents` | فقط فهرست اسناد آماده و مجاز |
| `GET /api/sources/{document_id}/sections/{section_id}?revision=...` | بررسی مجوز و revision جاری؛ 404 عمومی برای ناموجود/غیرمجاز |
| `GET, POST /api/manager/documents` | مدیر؛ فهرست پردازش یا بارگذاری |
| `PUT, DELETE /api/manager/documents/{document_id}` | مدیر؛ جایگزینی یا حذف منطقی فوری |
| `GET /api/manager/jobs/{job_id}` | مدیر؛ وضعیت پردازش غیرحساس |
| `GET /api/health` | وضعیت سلامت عمومی بدون credential یا اطلاعات DB |

وضعیت پیاده‌سازی این جدول: `POST`/`GET` روی `/api/manager/documents` و `GET` روی `/api/manager/jobs/{job_id}` در پارت ۸ پیاده شده‌اند؛ پارت ۹ رابط `/manager/documents`، proxy محدود و CLI اپراتوری corpus را افزوده است. پاسخ فهرست شامل `job_id` و `safe_error` است. `PUT` و `DELETE` متعلق به پارت ۱۰ هستند و هنوز route ندارند. پاسخ بارگذاری `202` است و `job_id`، `document_id`، `revision`، `status`، `attempt` و `safe_error` را برمی‌گرداند؛ متن سند، متن staging و جزئیات provider هرگز در پاسخ نمی‌آید.

خروجی عمومی پاسخ فقط `answer, claims, sources, abstained, request_id` است؛ retrieval hits و usage داخلی به client نروند. قرارداد استناد `SourceRef(document_id: str, section_id: str, revision: str)` است.


## 5. Architecture Diagram

```text
مرورگر فارسی (Next.js / RTL)
        │ same-origin /api/*، کوکی نشست
        ▼
Next.js Route Handler ──► FastAPI modular monolith
                              ├── Auth / authorization
                              ├── Documents / ingestion worker
                              ├── Hybrid retrieval / answer validation
                              ├── Ollama localhost:11434 (embedding 768d)
                              ├── OpenRouter (generation; model configurable)
                              └── OpenRouter rerank (اختیاری، پیش‌فرض خاموش)
                                        │
                                        ▼
                          PostgreSQL 16 host:5433
                         DB: enterprise_knowledge_copilot
```

این دیاگرام معماری پیشنهادی است. پیاده‌سازی DB در Compose ایجاد نمی‌کند؛ API و web به سرویس‌های native میزبان متصل می‌شوند.

## 6. Data Flow

### پرسش و پاسخ

1. کاربر پرسش را در UI می‌فرستد و Route Handler آن را از مسیر same-origin به FastAPI می‌رساند.
2. API نشست را با hash موجود در DB حل می‌کند و نقش جاری را از کاربر می‌خواند؛ هیچ role ارسالی از مرورگر معتبر نیست.
3. سرویس، دامنهٔ اسناد فعال، جاری، آماده و مجاز را در همان درخواست می‌سازد.
4. نسخهٔ نرمال‌شدهٔ پرسش به BM25 همان دامنه و Ollama با پیشوند `search_query:` می‌رود. هر مسیر حداکثر ۲۰ candidate می‌دهد؛ اجتماع حداکثر ۴۰ نامزد با RRF و `k=60` ادغام می‌شود.
5. در صورت تنظیم صریح rerank، حداکثر ۲۰ candidate مجاز به آن فرستاده می‌شود؛ پیش‌فرض خاموش است. حداکثر پنج قطعه/بخش برتر برای زمینه انتخاب می‌شود.
6. OpenRouter با مدل تنظیم‌شده JSON محدودشده به schema ادعا/نقل‌قول/SourceRef تولید می‌کند. backend ارجاع‌ها و نقل‌قول دقیق را با متن chunkهای واقعاً ارسال‌شده تطبیق می‌دهد.
7. backend مجوز جاری و revision را دوباره بررسی می‌کند. تغییر مجوز/نسخه باعث عدم تحویل پاسخ می‌شود. UI پاسخ اعتبارسنجی‌شده یا امتناع ثابت را نمایش می‌دهد.

قرارداد generation: `response_format` با JSON Schema و `provider.require_parameters=true`؛ پشتیبانی واقعی مدل منتخب بعد از درج کلید با smoke test بررسی شود. هر claim باید quote دقیق و SourceRef از قطعه‌های واقعاً ارسال‌شده داشته باشد. متن نهایی سمت سرور از claimهای معتبر و پیام‌های ثابت ساخته می‌شود؛ متن آزاد مدل یا missing_parts آزاد نمایش داده نشود. هر ادعای نامعتبر کل payload را رد می‌کند؛ حداکثر یک repair در سقف مشترک دو تلاش generation و deadline 60 ثانیه، سپس امتناع خنثی. timeout/خطای شبکه خطای عملیاتی است. تطبیق quote و schema صحت معنایی ادعا را ثابت نمی‌کند؛ ارزیابی انسانی لازم است.


### ورود یا جایگزینی سند

1. مدیر فایل Markdown یا متن UTF-8 را بارگذاری می‌کند؛ backend اعتبار، فراداده، حجم، سند/قطعه و سقف‌های محصول را پیش از فراخوانی provider بررسی می‌کند.
2. job با وضعیت `pending` ثبت می‌شود. یک worker می‌گیرد و lease ۱۲۰ثانیه‌ای را هر ۳۰ ثانیه تمدید می‌کند؛ حداکثر سه تلاش دارد.
3. متن و مرز عنوان‌ها حفظ می‌شود. هر chunk حداکثر ۱۲۰۰ نویسه و هم‌پوشانی ۱۵۰ نویسه دارد و هرگز از section عبور نمی‌کند. علاوه بر این سقف نویسه، chunker باید با tokenizer منطبق بر مدل، متن هر قطعه را به حداکثر ۴۰۰ token محدود کند؛ تخمین تقریبی پذیرفته نیست.
4. embedding برای هر قطعه با `search_document:` درخواست می‌شود. چون سقف token مدل Nomic برابر ۵۱۲ است، ارسال متن خام بلند با `truncate:false` انجام می‌شود تا ورودی بلند بی‌صدا بریده نشود؛ برش به‌وسیلهٔ chunker توکن‌آگاه در حد ۴۰۰ token انجام می‌شود.
5. محتوا و بردارهای revision جدید در staging نوشته می‌شوند. فقط پس از تکمیل همهٔ قطعه‌ها، یک تراکنش revision تازه را جاری می‌کند و revision قبلی را از جست‌وجو خارج می‌سازد.
پارت ۸ گام‌های ۱ تا ۵ را برای سند تازه پیاده کرد: بارگذاری مدیر سند را با سقف `.md`/`.txt` و ۱ MiB و UTF-8 می‌پذیرد، `document_id` و `target_revision` را سرور می‌سازد، job را `pending` ثبت می‌کند و سند را با `current_revision = NULL` می‌گذارد تا هیچ‌چیز پیش از فعال‌سازی قابل بازیابی نباشد. worker با `FOR UPDATE SKIP LOCKED` ادعا می‌کند، lease ۱۲۰ ثانیه‌ای می‌گیرد و هر ۳۰ ثانیه تمدید می‌کند؛ ادعا فقط تا وقتی معتبر است که توکن آن تازه **و** lease آن هنوز نگذشته باشد؛ چون انتظار روی قفل می‌تواند از عمر lease بگذرد و شرطِ هر statement پیش از انتظارِ خودش ارزیابی می‌شود، فعال‌سازی پس از هر انتظار قفل — از جمله پس از آخرین قفل و درست پیش از نخستین تغییر — lease را با ساعت زندهٔ پایگاه‌داده دوباره می‌سنجد. توکن باید تازه و lease هنوز معتبر باشد. سپس parse، قطعه‌بندی، بررسی سهمیه و embedding را انجام می‌دهد و در پایان یک تراکنش، revision را جاری و job را `ready` می‌کند.
6. شکست جایگزینی revision جاری قبلی را حفظ می‌کند. حذف/کاهش مجوز، سند را فوراً از دامنهٔ مجاز query خارج می‌کند. jobهای منقضی‌شده بعد از restart قابل بازیابی‌اند؛ fencing token و revision جاری مورد انتظار پیش از commit اتمی دوباره بررسی می‌شوند.

پارت ۱۰ گام‌های ۶ و مسیر جایگزینی/حذف را پیاده کرد. `PUT /api/manager/documents/{id}` یک job با `operation = replace` می‌سازد و `expected_current_revision` را زیر قفل سطر `documents` می‌خواند تا compare-and-swap دقیقاً همان مبنا را بسنجد. worker پیش از قطعه‌بندی، `sections` نسخهٔ مبنا را می‌خواند و شناسه‌ها را طبق قرارداد پایداری زیر بازتخصیص می‌دهد؛ chunkهای تازه با همان شناسه‌های نگه‌داشته‌شده نوشته می‌شوند، پس هر chunk همچنان به بخش خودش join می‌شود. هنگام فعال‌سازی، عنوان و سیاست در انتظار به مقادیر مؤثر منتقل و سپس پاک می‌شوند.

`DELETE /api/manager/documents/{id}` حذف منطقی است: `status` به `inactive` می‌رود، `current_revision` و ردیف‌های نسخهٔ منتشرشده می‌مانند، و در همان تراکنش هر job باز آن سند ناموفق و lease آن پاک می‌شود تا worker در حال اجرا در نوشتن بعدی‌اش متوقف شود. ترتیب قفل «قفل مشورتی ناشر، بعد سطر `documents`، بعد jobها» است و مجموعهٔ jobها **زیر قفل سند** خوانده می‌شود؛ بازبینی کاربر نشان داد که خواندن آن پیش از قفل سند، حذفی را که هم‌زمان با staging اجرا می‌شود از دید خود محروم می‌کند و job یتیم می‌گذارد. اگر job پیش از رسیدن به فعال‌سازی حذف نشده باشد، مسیر `DocumentDeletedError` در worker خودش آن را terminal و سطرهای stagingش را حذف می‌کند. پاسخ همیشه `204` است، از جمله برای شناسهٔ ناشناخته و سند ازپیش حذف‌شده، تا retry و دوبار کلیک خطا نشوند. صفحهٔ مدیر برای هر سند کنترل «جایگزینی نسخه» (فرم عنوان/نقش/فایل) و «حذف سند» با تأیید دومرحله‌ای دارد، وضعیت `inactive` را نشان می‌دهد و هر دو کنترل را وقتی jobی در جریان است غیرفعال می‌کند تا کاربر به پاسخ `409` نرسد. دو نکتهٔ رابط که بازبینی کاربر پیدا کرد: فیلدهای فرم با `key` روی مقدار سرور remount می‌شوند، چون `defaultValue` فقط در mount خوانده می‌شود و بدون آن پس از تازه‌سازی نقش تازه نمایش داده نمی‌شد در حالی که ویرایش کاربر هم باید حفظ می‌شد؛ و «نمایه‌شده» از فیلد تازهٔ `has_published_revision` می‌آید که مستقیماً از `current_revision` ساخته می‌شود، نه از وضعیت آخرین job — یک جایگزینی در جریان یا ناموفق چیزی دربارهٔ وجود نسخهٔ منتشرشده نمی‌گوید، و `version` هم نمی‌تواند جای آن را بگیرد چون نسخهٔ اعلامی است و فایل نامطمئن می‌تواند خودش مقدار `unpublished` را اعلام کند.

پارت ۹ import اولیه را با `uv run --locked python -m app.cli.import_corpus --manager-login manager` (گزینهٔ مدیر قابل تغییر است) اجرا می‌کند؛ worker موجود پس از آن jobها را پردازش می‌کند. CLI تمام ۲۰ فایل ثابت corpus را پیش از هر نوشتن بررسی می‌کند، شناسه‌های ثابت را حفظ و نقش را از allowlist اپراتوری می‌گیرد. اجرای مجدد بدون تغییر منبع idempotent است؛ هر شناسهٔ موجود با متن یا سیاست متفاوت رد می‌شود و این فرمان job ناموفق را retry نمی‌کند. صفحهٔ مدیر فهرست را هر پنج ثانیه تازه می‌کند، upload را می‌فرستد و وضعیت job را با `job_id` آخرین پردازش در همان فهرست پیگیری می‌کند؛ proxy فقط مسیرهای لازم را عبور می‌دهد.

قرارداد تکمیلی ورود سند: فایل فاقد شناسهٔ بخش، از سرور section_id ترتیبی پایدار می‌گیرد؛ در جایگزینی، نگاشت بخش‌های حفظ‌شده باقی می‌ماند و بخش تازه شناسهٔ آزاد بعدی می‌گیرد. تغییر سیاست دسترسی نباید نسخهٔ قبلی را برای کاربران تازه‌مجازشده قابل مشاهده کند؛ کاهش دسترسی فوری است، اما گسترش دسترسی فقط پس از ready و فعال‌سازی revision تازه اعمال می‌شود. مجوز مؤثر revision جاری باید از سیاست staging جدا بماند.

پارت ۱۰ «شناسهٔ آزاد بعدی» را از نظر امنیتی روشن کرد، چون تعبیر ساده‌اش غلط است: شناسهٔ آزاد یعنی **بالاتر از بالاترین شناسه‌ای که آن سند تاکنون استفاده کرده**، نه کوچک‌ترین شناسهٔ بلااستفاده. اگر شناسهٔ آزادشده دوباره داده شود، هر استنادی که به بخش حذف‌شده اشاره می‌کرد بی‌صدا متن بخش دیگری را نقل می‌کند. بخش‌های حفظ‌شده بر پایهٔ **عنوان** تطبیق داده می‌شوند، چون جایگاه بخش پایدار نیست و سند parse‌شده هیچ کلید ماندگار دیگری ندارد؛ عنوانِ بازنویسی‌شده یعنی بخش تازه. `apps/api/app/ingestion/sections.py` این قاعده را خالص و بدون I/O نگه می‌دارد تا کامل بدون پایگاه‌داده آزمون‌پذیر باشد.

بازبینی کاربر یک شکاف واقعی در همین قاعده نشان داد: «بالاترین شناسهٔ استفاده‌شده» اگر از revision جاری خوانده شود کافی نیست، چون revision جاری همیشه بیشترین شناسهٔ خودش را دارد ولی ممکن است شناسه‌ای که جایگزینی قبلی حذف کرده دیگر در آن نباشد. بنابراین `store.read_section_identity` mark را روی همهٔ revisionهای آن سند می‌گیرد و آن را به‌عنوان ورودی به `stable_section_ids` می‌دهد. این کار به سیاست نگه‌داری ردیف‌های نسخهٔ منتشرشده وابسته است و در `DATABASE.md` همین وابستگی ثبت شده.

جداسازی «مجوز مؤثر» از «سیاست staging» در پارت ۱۰ با دو ستون `documents.staged_access_role` و `documents.staged_title` انجام شد. یک قاعدهٔ واحد پشت آن است: **هر چیزی جز باریک‌تر کردن دسترسی، فقط در فعال‌سازی عوض می‌شود.** باریک‌تر کردن استثناست چون `SECURITY.md` آن را فوری می‌خواهد؛ بقیهٔ staging — عنوان — دلیل ندارد زودتر اعمال شود، چون در صورت شکست، سندی با نام تازه روی متن کهنه می‌ماند.

قرارداد retry: embedding و rerank هرکدام حداکثر دو تلاش 10ثانیه‌ای دارند؛ generation حداکثر دو تلاش 30ثانیه‌ای دارد و network retry و JSON repair همین سهمیه را مشترک مصرف می‌کنند. deadline مشترک درخواست 60 ثانیه است. فقط خطای شبکه و 429/502/503/504 با backoff نمایی و jitter در زمان باقی‌مانده retry شوند؛ خطای قطعی parsing یا ابعاد نامعتبر retry بی‌حد نگیرد. اثر خارجی قبل از crash می‌تواند دوباره اجرا شود؛ تضمین exactly-once برای فراخوانی provider داده نمی‌شود.

## 7. Project Structure

پارت ۲ پایهٔ `apps/web/` را با Next.js App Router، TypeScript و رابط فارسی RTL اضافه کرد. Part 5 صفحهٔ `/login`، پوستهٔ shell با نقش `employee` یا `manager` از پاسخ سروری `/api/auth/me`، و خروج از حساب را اضافه می‌کند. مسیر `/` برای نشست نامعتبر به ورود هدایت می‌شود؛ درخواست `/me` از server با کوکی نشست و `no-store` انجام می‌شود. صفحهٔ `/manager/documents` فقط برای مدیر نمایش داده می‌شود. Route Handler auth به `/api/auth/[action]` محدود است؛ proxy مدیریت در `/api/manager/[...path]` فقط مسیرهای فهرست/بارگذاری اسناد، یک سند مشخص و وضعیت job را عبور می‌دهد. پارت ۱۰ به همین proxy `PUT` و `DELETE` را روی یک سند اضافه کرد، با allowlist شکل شناسه، با الزام Origin برای هر نوشتن (نه صرفاً تحمل آن)، با همان سقف بدنه، و با پاسیدن `204` بدون ساختن بدنه. مجوز واقعی در API اعمال می‌شود؛ جزئیات مرز امنیتی در SECURITY آمده است. تنظیم‌های سروری `API_BASE_URL` و `WEB_ORIGIN` از environment بر فایل `.env` ریشه اولویت دارند؛ هیچ secret به client expose نمی‌شود. بررسی‌های هدفمند موفق‌اند و پارت برای انتشار تأیید شده است.

پارت ۱۶ صفحهٔ `/ask` و proxy مسیر پاسخ را در `/api/answers` افزود. صفحهٔ سرور فقط هویت را می‌خواند و ریدایرکت می‌کند و مرز مجوز در API می‌ماند، چون آنجا allowlist واقعی است. proxy فقط `POST` می‌پذیرد، Origin وب را الزام می‌کند، سقف بدنهٔ ۶۴ KiB را هنگام stream اعمال می‌کند و `Retry-After` را عبور می‌دهد. مهلت proxy برای این مسیر ۷۰ ثانیه است؛ auth ده ثانیه و manager پانزده ثانیه می‌مانند. قرارداد پاسخ با `answerContractFrom` در مرز اعتبارسنجی می‌شود. `sources` عنوان ندارند و پارت ۱۷ آن را اضافه می‌کند. متن نهایی `answer` عیناً نمایش داده می‌شود؛ فقط فهرست استنادها ادعاهای هم‌متن را گروه‌بندی می‌کند. شمارش بدنه در تابع خالص `readBounded` است و خطاهای هویت و stream در مرز خطای proxy نگه داشته می‌شوند. فهرست اسناد واقعی متعلق به پارت ۱۷ است.

پارت ۳ ماژول `apps/api/app/db/`، `apps/api/alembic/`، `apps/api/alembic.ini` و `apps/api/sql/provision.sql` را افزود و migration `0001` را روی پایگاه اختصاصی اجرا کرد. این ماژول کنار `domain/` قرار دارد چون مدل ORM به SQLAlchemy وابسته است و `domain` نباید به framework وابسته شود: `base.py` قرارداد نام‌گذاری قیدها، `models.py` هفت جدول، `url.py` ساخت URL با allowlist، `engine.py` engine و session factory و `preflight.py` بررسی پیش‌نیاز `vector`. `alembic.ini` هیچ connection string یا credentialی ندارد؛ URL در `alembic/env.py` از `Settings` ساخته و پیش از اتصال با allowlist بررسی می‌شود. افزونهٔ `vector` بخشی از migration نیست و با `sql/provision.sql` یک‌بار توسط superuser سرویس موجود ساخته می‌شود. `GET /api/health` هنوز فقط liveness است و اتصال DB را بررسی نمی‌کند.
در پارت ۱، `apps/api/app/` (factory برنامه، تنظیمات و route سلامت)، `apps/api/tests/` و manifest/lockfile ساخته شدند. `auth/` و `domain/` برای پارت ۴ موجودند. پارت ۶ `documents/` را برای parse قطعی، chunking توکن‌آگاه، نرمال‌سازی متن جست‌وجو و tokenizer افزود؛ پارت ۸ `ingestion/` را برای ذخیره و پردازش پایدار گسترش داد و پارت ۹ `cli/import_corpus.py` و رابط مدیر را افزود. adapter embedding در `providers` موجود است؛ پارت ۱۱ `retrieval` را افزود و پارت ۱۴ `answer` را برای اعتبارسنجی نقل‌قول، ساخت متن از claimهای تأییدشده و دروازهٔ نهاییِ تحویل؛ `evaluation` در پارت ۱۸ و پس از آن ساخته می‌شود. `GET /api/health` فقط liveness را با `{"status":"ok"}` گزارش می‌کند و اتصال DB یا provider را بررسی نمی‌کند. تنظیمات API از `.env` ریشه با تقدم متغیرهای محیط فرایند خوانده می‌شوند. خطای تنظیمات نامعتبر هنگام شروع، فقط نام فیلد و نوع خطا را نشان می‌دهد. logging دسترسی خام در فرمان اجرای محلی خاموش است تا query string ثبت نشود.

## 8. Dependency Rules

- UI فقط با API هم‌مبدأ حرف می‌زند؛ UI و Route Handler مستقیماً DB یا provider را صدا نمی‌زنند.
- routeها transport و schema را مدیریت می‌کنند؛ مجوز و قواعد دامنه در service نیز دوباره بررسی می‌شوند.
- ماژول سند مالک ساخت revision و ingestion است؛ بازیابی فقط از دادهٔ فعال/جاری/آماده استفاده می‌کند.
- retrieval به adapter embedding وابسته است، نه به SDK یک vendor. generation و reranking نیز پشت قرارداد adapter می‌مانند.

پارت ۱۲ همان خط سیر را کامل کرد: `rerank` بین RRF و برش نهایی نشست، یعنی حداکثر `rerank_top_k` نامزد پس از ادغام، سپس rerank، سپس حداکثر `final_top_k` نتیجه. adapter در `app/providers/rerank.py` است و قراردادهای `ScoredCandidate`، `RerankCandidate`، `ProviderUsage` و پروتکل `RerankProvider` در `app/providers/base.py` کنار پروتکل‌های embedding زندگی می‌کنند، چون هر دو لایه به آن‌ها نیاز دارند و هیچ‌کدام نباید تعریفشان کنند.

**تلاش دوم rerank بدنه را از نو می‌سازد.** `arun_with_retry` هر تلاش یک تازه‌ساز را صدا می‌زند و adapter تازه‌ساز را به فراخواننده می‌دهد، تا دروازهٔ مجوز پیش از **هر** ارسال دوباره اجرا شود نه فقط پیش از اولی. دلیلش ساختاری است: بدنهٔ آماده پیش از حلقه، متن تلاش اول را در تلاش دوم عیناً می‌فرستاد. اگر تازه‌سازی خالی شود، درخواست fail-closed رد می‌شود؛ ارسال فهرستی کوتاه‌تر رد می‌شود چون شمارش پاسخ با عددی سنجیده می‌شد که واقعاً فرستاده نشده بود. حلقهٔ retry دست‌نویس نشده؛ همان helper مشترک استفاده می‌شود تا deadline و سهمیهٔ retry در یک جا بماند.

**تلاش موفق، فهرست خودش را تحویل می‌دهد.** `operation` به‌جای خودِ payload، سه‌تایی `(payload, sent, effective_top_n)` برمی‌گرداند و نگاشت با همان `sent` انجام می‌شود. یک `index` در پاسخ جایگاهی در فهرستی است که **همان تلاش** فرستاده، پس نگاشت علیه `candidates` اولیه هم غلط می‌نشاند و هم شمارش را علیه درخواستی که ارسال نشده می‌سنجد. بازگرداندن این سه‌تایی از خودِ `arun_with_retry` ممکن است چون نوع بازگشتی آن generic است — نیازی به حلقهٔ دستی یا حالت مشترک نیست.

پارت ۱۳ تولید ساختاریافته را اضافه کرد: `app/providers/generation.py` روی `POST /chat/completions` با `response_format` از نوع `json_schema` و `strict: true`. قرارداد دامنه — `Claim`، `EvidenceItem`، `GenerationResult` و `MissingPart` — کنار پروتکل `GenerationProvider` در `app/providers/base.py` زندگی می‌کند، چون فراخواننده باید بتواند بدون import کردن adapter نام ببرد چه چیزی دریافت می‌کند. خطاهای adapter محلی‌اند، همین‌طور که `RerankProviderError` محلی است.

سه تصمیم که ارزش ثبت دارند:

- **`require_parameters: true` تنظیم می‌کنیم و کمینه پارامتر می‌فرستیم.** دلیلش سلیقه نیست: مستندات رسمی می‌گویند پارامتر پشتیبانی‌نشده **نادیده گرفته** می‌شود، پس بدون این تنظیم schema یک درخواست است و نه یک تضمین. و چون همین تنظیم endpoint ناسازگار را کنار می‌گذارد، هر پارامتر اضافه یعنی یک راه دیگر برای غیرقابل‌مسیریابی‌شدن یک endpoint سالم. `temperature` عمداً فرستاده نمی‌شود.
- **حلقهٔ تلاش دست‌نویس است، و این بار دلیلش واقعی است.** `arun_with_retry` «همان عملیات را دوباره اجرا کن» را قرارداد می‌کند، ولی repair درخواست **متفاوتی** می‌فرستد — یکی که به مدل می‌گوید خروجی قبلی‌اش قابل استفاده نبود. جا کردن آن در آن کمک یعنی پرتاب `RetryableError` برای نقصی دائمی، و آن خطا اگر بیرون بزند در حالی که گذراست جعل می‌شود — همان باگی که adapter پارت ۱۲ داشت. سه پیامد جدا در حلقه تعریف شده: گذرا، قابل repair، و رد‌شده.
- **`POST /api/answers` و `/api/sources` مرز پاسخ‌اند.** `app/api/answers.py` و `app/api/documents.py` تنها جاهایی هستند که متن سند از فرایند عبور می‌کند، و هر دو `Cache-Control: no-store` می‌گذارند چون محتوایشان برای هر کاربر است و cache عمومی آن را به خوانندهٔ بعدی می‌دهد. پاسخ دقیقاً پنج کلید دارد و همین در آزمون قفل شده. مهلت کل ۶۰ ثانیه‌ای قرارداد سراسری اینجا برای اولین بار اجرا می‌شود، چون اولین endpointی است که در دامنهٔ درخواست به بیرون فراخوانی می‌کند؛ و `asyncio.timeout` خطای آشکار می‌دهد، نه پاسخ نیمه‌ساخته.
- **`UploadGuard` یک middleware است با یک شمارنده و دو سقف، نه یک سقف برای یک مسیر.** سقف روی مدل درخواست دیر است: FastAPI کل بدنه را پیش از هر dependency پارس می‌کند. مسیر upload سقف multipart دارد (فایل به‌علاوهٔ framing) و `POST /api/answers` سقف ۶۴ KiB برای JSON، چون آنجا فایلی در کار نیست و بازاستفاده از عدد multipart سقفی می‌بود که هیچ بدنهٔ موجهی به آن نمی‌رسد. شمارش روی جریان است نه روی `Content-Length`. دو چیز در اینجا از بازبینی پارت ۱۵ آمد و هر دو در `SECURITY.md` بخش ۸ شرح داده شده‌اند: خطای سرریز باید `HTTPException` باشد تا ۴۱۳ از parser استارلِت بیرون بیاید، و خطاهای provider که retrieval می‌دهد باید در endpoint گرفته شوند وگرنه پرسش کاربر به traceback می‌رود.
- **`build_provider` کلاینت را از فراخواننده می‌گیرد.** کلاینتی که adapter آن را نگه می‌دارد باید مالکی داشته باشد که آن را می‌بندد؛ مسیر پاسخ همان کلاینتی را می‌سازد که برای generation هم لازم دارد و یک `aclose` هر دو را می‌بندد. worker کلاینت خودش را می‌گیرد و نمی‌بندد، چون فرایند یک‌بارمصرف است و در آنجا نشتی وجود ندارد.
- **`_rerank_builder` یک درز آزمون نام‌دار است، نه یک سربارگذاری.** خطاهایی که اهمیت دارند — بدنهٔ upstream غیرقابل‌retry و کلید غایب — **خاصیت ساخت پیام در adapter واقعی‌اند**. آزمونی که factory را استاب کند دربارهٔ آن‌ها چیزی نمی‌گوید و در عین حال سبز می‌شود، چون provider ساخته می‌شود و کار می‌کند. بنابراین مسیر از یک تابع نام‌دار رد می‌شود تا آزمون بتواند **builder** را عوض کند نه خود factory را، و در نتیجه adapter واقعی با کلاینت واقعی ساخته می‌شود و تنها transport آن تغییر می‌کند.
- **بستهٔ `answer/` مالک متن سروشده است.** `quotes.py` نگاشتِ فقط-مقایسه‌ای می‌سازد و بازهٔ عیناً از passage برمی‌گرداند؛ `validate.py` همهٔ claimها را یک‌جا می‌پذیرد یا رد می‌کند؛ `compose.py` متن نهایی را از claimهای پذیرفته و جمله‌های خنثای ثابت می‌سازد؛ `service.py` جریان کامل و دروازهٔ نهایی را می‌چیند. سقف claimها (`MAX_CLAIMS`) اینجاست چون `GENERATION_SCHEMA` روی `claims` حد `maxItems` ندارد و افزودنش به schema ریسک رد شدن کل درخواست را دارد — پارامتر پشتیبانی‌نشده نادیده گرفته می‌شود و با `require_parameters` نادیده‌گرفتن به رد درخواست تبدیل می‌شود.
- **`GenerationProvider` پروتکل است، نه جزئیات.** `refresh` در امضای پروتکل هست تا فراخوانیِ دروازهٔ مجوز از راه نوع‌دهی ممکن باشد؛ بدون آن `answer` یا باید `Any` می‌کرد یا cast، و هر دو دروازهٔ خروجی را بی‌صدا دور می‌زدند.
- **`GenerationResult.answer` هرگز نمایش داده نمی‌شود.** مدل ممکن است نثر بنویسد و آن نثر حفظ می‌شود، ولی متن سروشده در پارت ۱۴ از claimهای تأییدشده ساخته می‌شود. دلیل نگه‌داشتنش این است که یک اپراتور بتواند ببیند مدل چه گفته بود — بدون اینکه گزارش آن را به کاربر نشان دهد.

**سقف توکن از اندازه‌گیری آمد، نه از سلیقه.** با پنج قطعهٔ فارسی واقعی، completion بین ۲۹۱ تا ۲۱۱۸ توکن نوسان داشت و سقف ۱۵۰۰ بخشی از اجراها را با `finish_reason: "length"` قطع می‌کرد؛ سقف پیش‌فرض روی ۴۰۹۶ نشسته، یعنی بالای بدترین مقدار مشاهده‌شده. مرز واقعی تأخیر، مهلت ۳۰ ثانیه‌ای هر تلاش است نه این عدد.

یک تصمیم که ارزش ثبت دارد: **تعداد نتایج با `min(top_n, len(candidates))` سنجیده می‌شود، نه با یک ثابت.** اگر پنج نامزد فرستاده شود، پاسخ باید دقیقاً پنج نتیجه داشته باشد؛ سنجش با ۲۰ همیشه شکست می‌خورد و همیشه‌پاس می‌دهد و هیچ‌کدام از رفتار واقعی نیست. همچنین `rerank_hits` خودش به `final_top_k` نمی‌بُرد: بریدن فهرست پیش از rerank یعنی گرفتن گزینه‌ها از مدل و بعد رتبه‌بندیِ بی‌معنا؛ برش نهایی در `retrieve` انجام می‌شود که هر دو اندازه را می‌داند.

پارت ۱۱ بستهٔ `apps/api/app/retrieval/` را ساخت: `store.py` پیشوند allowlist، `lexical.py` نمره‌دهی BM25، `fusion.py` ادغام RRF، `service.py` تابع `retrieve` و `contracts.py` شکل `RetrievalConfig`/`RetrievalHit`/`SourceRef`. وابستگی تازه `rank_bm25` است که در قرارداد هم نام برده شده بود.

سه تصمیم در این پارت بار امنیتی دارد و هر سه در کد توضیح داده شده‌اند:

- **دو query با snapshot یکسان مجوز را حل نمی‌کنند.** رتبه‌بندی روی snapshot است و دسترسی میان خواندن و پاسخ می‌تواند باریک‌تر شود، سند حذف شود یا نسخه جایگزین گردد؛ رتبه‌بندی چیزی را از رتبه خارج نمی‌کند. پس candidateهای ادغام‌شده **پیش از بازگرداندن یک‌بار دیگر زیر همان allowlist خوانده می‌شوند** و آنچه دیگر مجاز نیست حذف می‌شود. متن hit هم از همین خواندن تازه می‌آید، پس هر hit متنی را نقل می‌کند که *همین حالا* مجاز است. اگر جایگزینی در میانه رخ دهد، نتیجه کمتر می‌شود نه اینکه با رتبهٔ متن دیگری پر شود.
- **دامنهٔ مجاز پیش از رتبه‌بندی با provenance سنجیده می‌شود.** `store.assert_index_consistent` پیش‌بررسی دامنهٔ مجاز را انجام می‌دهد؛ سپس هر query رتبه‌بندی provenance را از همان ردیف SQL که مصرف می‌کند می‌گیرد و با provider پرس‌وجو تطبیق می‌دهد: ردیف‌های واژگانی پیش از BM25، ردیف‌های برداری پیش از RRF، و ردیف‌های تازهٔ گیت نهایی پیش از بازگشت. بنابراین انتشار هم‌زمان نسخه‌ای با digest دیگر نمی‌تواند نتیجه‌ای را با بردار پرس‌وجوی مدل قبلی وارد رتبه‌بندی یا خروجی کند. ناسازگاری fail-closed است. این بررسی به **دامنهٔ مجاز** محدود است نه کل جدول `chunks`: حکم سراسری، در دسترس‌بودن یک کاربر را به ردیف‌هایی وابسته می‌کرد که حق ندارد بداند وجود دارند، و خودِ رد کردن یک سیگنال است. پیام خطا هویت *مورد انتظار* و تعداد provenanceهای ناسازگار را می‌گوید و هیچ نام سند و هیچ digest *مشاهده‌شده* را لو نمی‌دهد.
- **پرسش یک‌بار نرمال می‌شود و همان رشته به هر دو مسیر می‌رود.** پیشوند adapter نرمال‌سازی قراردادی این پروژه نیست؛ فرستادن متن خام یعنی دو املای معادل فارسی بردار متفاوت بسازند و دو مسیر دنبال دو چیز متفاوت بگردند. متن اصلی پرسش برای نمایش دست‌نخورده می‌ماند.
- **allowlist یک پیشوند SQL است، نه فیلتر پس از بازیابی.** اگر رتبه‌بندی روی همهٔ ردیف‌ها انجام و بعد حذف شود، شمار نتایج به اسناد غیرمجاز وابسته می‌شود و ایمنی به فراموش‌نشدن یک فیلتر گردایده می‌ماند. هر دو مسیر از یک عبارت واحد ساخته می‌شوند.
- **«تطبیق واژگانی» با هم‌پوشانی توکن تصمیم می‌گیرد، نه با علامت نمره.** `rank_bm25` مقدار IDF را وقتی منفی شود روی کسری از *میانگین* IDF مجموعه می‌گذارد و روی مجموعهٔ کوچک، جایی که یک واژه در همهٔ قطعه‌ها هست، آن میانگین هم منفی است؛ پس قطعه‌ای که کاملاً مطابقت دارد نمرهٔ منفی می‌گیرد. آزمون `score > 0` در آن حالت برای پرسشی که همه‌جا مطابقت دارد هیچ نتیجه‌ای برمی‌گرداند. هم‌پوشانی دقیق است و به حساب کتابخانه وابسته نیست.
- **شرط `embedding IS NOT NULL` در predicate مشترک است، نه فقط در مسیر برداری.** `DATABASE.md` بخش ۵ دادهٔ فاقد embedding را از retrieval بیرون می‌گذارد؛ اگر شرط فقط در مسیر برداری باشد، BM25 راه دور زدن قاعده‌ای می‌شود که دربارهٔ *داده* است نه دربارهٔ الگوریتم. قطعه‌ای که وجود دارد ولی هرگز embed نشده ناقص است و ردیف ناقص نباید قابل استناد باشد.
- **ترتیب برداری با فاصله شروع می‌شود.** `order_by` در SQLAlchemy **اضافه** می‌کند و جایگزین نمی‌کند؛ اگر query مشترک `ORDER BY chunk_id` داشت، query برداری به `ORDER BY chunk_id, embedding <=> $1` تبدیل می‌شد و عملاً با UUID مرتب می‌شد. `chunk_id` فقط بعد از فاصلهٔ برابر می‌آید و فقط برای بازتولیدپذیری تساوی.

بدون route عمومی (پارت ۱۵ آن را می‌سازد)، بدون تغییر schema، و بدون هیچ مسیر جایگزین: شکست در اینجا شکست است، چون افت خاموش آنچه را تماشاگر می‌بیند بی‌خبر عوض می‌کند.
- همهٔ مسیرهای بازیابی، rerank، زمینهٔ مدل و پاسخ از یک دامنهٔ مجاز ساخته‌شده سمت سرور استفاده می‌کنند؛ هیچ مرحله‌ای مجاز به گسترش آن نیست.
- مدل embedding و بُعد بردار در یک نمایه باید یکسان باشند؛ تغییر مدل نیازمند نمایهٔ تازه و جابه‌جایی اتمی است.
- secrets فقط در محیط سرویس می‌مانند؛ مقدار secret، متن خام پرسش، prompt و محتوای سند وارد لاگ عادی نمی‌شوند.

## 10. Performance Considerations

- در هر درخواست، ۲۰ نتیجهٔ واژگانی و ۲۰ نتیجهٔ برداری حداکثر، ادغام با RRF `k=60`، حداکثر ۲۰ ورودی rerank اختیاری و حداکثر پنج قطعه برای زمینه در نظر گرفته می‌شود.
- دو مسیر lexical/vector روی دامنهٔ مجاز همان درخواست به‌صورت موازی اجرا می‌شوند؛ BM25 از `rank_bm25` استفاده می‌کند و متن منبع برای quote دست‌نخورده می‌ماند.
- ابتدا اسکن دقیق pgvector برای اندازهٔ کوچک داده کافی است؛ ANN تنها پس از اندازه‌گیری latency و رشد واقعی داده بررسی می‌شود.
- سقف آغازین بارگذاری ۱ MiB، ۱۰۰ سند فعال و ۲۰۰۰ قطعهٔ جاری در طرح فنی آمده است؛ پس از parsing سهمیه پیش از هر provider call سنجیده می‌شود.
- chunking هم سقف ۱۲۰۰ نویسه با ۱۵۰ نویسه overlap در همان section و هم سقف ۴۰۰ token دارد؛ مرز section حفظ می‌شود.
- timeout کل پاسخ ۶۰ ثانیه است؛ سقف تلاش generation برابر ۳۰ ثانیه، embedding پرسش ۱۰ ثانیه و rerank ۱۰ ثانیه، همگی در همان deadline کلی قرار می‌گیرند.
- زمان p50/p95، retry، خطا و هزینه بر اساس دادهٔ ثبت‌شده گزارش می‌شوند؛ پیش از اندازه‌گیری ادعای عملکرد نمی‌شود.

## 11. Scalability Considerations

- نسخهٔ اول یک نمونهٔ API و worker با یک کار ingestion هم‌زمان دارد؛ lease job برای بازیابی پس از restart و جلوگیری از commit worker قدیمی است.
- در بیش از ۱۰۰ سند یا ۲۰۰۰ chunk، یا در صورت latency نامناسب اندازه‌گیری‌شده، سقف‌ها و راهبرد index/صف بازبینی می‌شوند. ANN، صف بیرونی و worker موازی پیش‌فرض نیستند.
- provider، نام مدل، digest و بعد بردار در هر chunk ذخیره می‌شوند. اگر digest مدل `:latest` تغییر کند، query به‌صورت fail-closed متوقف و کل index پروژه در staging دوباره ساخته می‌شود؛ index جدید فقط پس از تکمیل همهٔ بردارها به‌صورت اتمی فعال می‌شود. بردارهای دو digest مخلوط نمی‌شوند.
- پاک‌سازی فیزیکی revisionهای قدیمی، backup/restore و نگهداری telemetry بلندمدت نیازمند طرح عملیاتی جداگانه پیش از استقرار است.

## 12. Failure Scenarios

| رخداد | رفتار مورد انتظار |
|---|---|

| نقش یا سند حین پاسخ تغییر می‌کند | مجوز و revision پیش از پاسخ/منبع دوباره بررسی می‌شوند؛ پاسخ مبتنی بر دادهٔ منسوخ تحویل نمی‌شود. داده‌ای که قبلاً به provider مجاز فرستاده شده قابل پس‌گرفتن نیست. |
