# طرح فنی پیشنهادی: دستیار دانش سازمانی سپهر داده

## وضعیت و مرز تصمیم‌ها

این سند یک پیشنهاد فنی برای پیاده‌سازی نسخهٔ اول است؛ در مخزن فعلی برنامه و API هنوز پیاده نشده‌اند؛ فقط embedding محلی با دو متن آزمایشی بررسی شده است. رفتار محصول باید با [مشخصات نسخهٔ اول](mvp-spec.md)، داده‌های ساختگی [corpus](../../corpus) و [راهنمای ارزیابی](../evaluation-guide.md) سازگار بماند. اعداد بازیابی و محدودیت‌هایی که در این سند آمده‌اند نقطهٔ شروع پیشنهادی‌اند و باید با دادهٔ توسعه و اجرای واقعی بازبینی شوند؛ هیچ نتیجهٔ کیفیت، امنیت، سرعت یا هزینه‌ای را تضمین نمی‌کنند.

انتخاب چارچوب‌ها و کتابخانه‌های زیر پیشنهاد این طرح است. OpenRouter برای تولید پاسخ، Ollama برای embedding و سرور pgvector موجود انتخاب کاربر هستند؛ rerank با Cohere اختیاری و به‌صورت پیش‌فرض خاموش است. احراز هویت و سیاست ساخت حساب در مشخصات محصول تعیین نشده است؛ این سند پیش‌فرض اجرایی پیشنهاد می‌کند.

## نمای کلی

پیشنهاد استقرار محلی شامل رابط وب Next.js با TypeScript، backend ماژولار FastAPI روی Python 3.12 و یک PostgreSQL واحد با افزونهٔ pgvector است. سرور موجود `rag-postgres` با PostgreSQL 16.15 و pgvector 0.8.6 روی پورت 5433 در بررسی خواندنی 2026-10-04 تأیید شد. دیتابیس مستقل `enterprise_knowledge_copilot` و حساب محدود مختص پروژه در مرحلهٔ ساخت ایجاد خواهند شد؛ هیچ migration روی دیتابیس‌های قبلی اجرا نمی‌شود. پردازش سند در همان backend و با یک worker کنترل‌شده انجام می‌شود. برای نسخهٔ اول صف یا سرویس جداگانه‌ای مانند Redis/Celery لازم نیست. رابط فارسی و راست‌به‌چپ است و درخواست‌های مرورگر از مسیر same-origin در Next.js به API داخلی هدایت می‌شوند.

```text
مرورگر (Next.js، RTL)
       │ same-origin /api/*؛ نشست HttpOnly
       ▼
Next.js Route Handler ──► FastAPI (ماژول‌های منطقی)
                              │
                 ┌────────────┴─────────────┐
                 ▼                          ▼
          PostgreSQL + pgvector       Adapterهای ارائه‌دهنده
       کاربران، اسناد، قطعه‌ها،       تولید / embedding /
       نشست‌ها، اجراها و وضعیت کار    بازرتبه‌بندی (قابل‌تعویض)
```

این مرزبندی مسئولیت‌هاست؛ API و worker در یک سرویس اجرایی هستند. در اجرای اولیه، Next.js و FastAPI روی میزبان اجرا می‌شوند و از PostgreSQL موجود در `127.0.0.1:5433` و Ollama در `127.0.0.1:11434` استفاده می‌کنند؛ کانتینر DB تازه ساخته نمی‌شود. localhost داخل کانتینر مقصد میزبان نیست؛ کانتینری‌کردن برنامه به بررسی جداگانهٔ شبکه نیاز دارد. API در این نسخه با یک فرایند اجرا می‌شود و ingestion loop فقط یک کار هم‌زمان دارد؛ توسعهٔ محلی با auto-reload نباید workerهای تکراری بسازد.

### پیشنهاد ارائه‌دهنده و مدل

OpenRouter برای تولید پاسخ انتخاب شده است. مقدار آغازین `OPENROUTER_MODEL=google/gemini-2.5-flash` قابل تغییر می‌ماند. درخواست تولید از JSON Schema محدودشده با `response_format` و `provider.require_parameters=true` استفاده می‌کند. پیش از تکیه بر این قرارداد، endpoint و مدل انتخابی باید با smoke test بررسی شوند؛ اگر provider پارامتر لازم را نپذیرد، برنامه نباید بی‌صدا آن را حذف کند یا به پاسخ بدون schema تکیه کند.

برای embedding از Ollama و مدل `nomic-embed-text-v2-moe:latest` استفاده می‌شود. شناسهٔ محلی `ff9c2f10ef5e` و خروجی 768 بُعدی با دو ورودی فارسی در 2026-10-04 تأیید شدند؛ این smoke test ارزیابی کیفیت retrieval نیست. endpoint برابر `POST /api/embed` است، برای سند پیشوند `search_document: ` و برای سؤال `search_query: ` افزوده می‌شود، `truncate=false` و کنترل شمار/ابعاد/مقادیر finite الزامی‌اند. مدل محدودیت 512 توکن دارد؛ بودجهٔ آغازین هر ورودی کامل با prefix برابر 400 توکنِ tokenizer منطبق با مدل است. متن بلند باید پیش از ارسال شکسته شود؛ سؤال بلند با پیام درخواست کوتاه‌سازی رد می‌شود، نه حذف خاموش انتهای آن. تغییر digest یا ابعاد نیازمند بازنمایه‌سازی کنترل‌شده است.

بازرتبه‌بندی Cohere `rerank-v4.0-fast` اختیاری است و `RERANK_ENABLED=false` پیش‌فرض دارد. `COHERE_API_KEY` فقط هنگام فعال‌سازی لازم است؛ برای embedding هیچ کلید Cohere لازم نیست. `OPENROUTER_API_KEY` در `.env` محلی خالی آماده شده است. مصرف Ollama محلی API bill ندارد؛ هزینهٔ سخت‌افزار اندازه‌گیری نشده و صفر ادعا نمی‌شود.

منابع قرارداد: [مدل Ollama](https://ollama.com/library/nomic-embed-text-v2-moe)، [کارت رسمی Nomic](https://huggingface.co/nomic-ai/nomic-embed-text-v2-moe).

قراردادهای adapter پیشنهادی: `EmbeddingProvider.embed_documents(texts) -> list[Embedding]`, `EmbeddingProvider.embed_query(text) -> Embedding`, `GenerationProvider.generate(messages, response_schema) -> GenerationResult`, و `Reranker.rerank(query, candidates) -> list[ScoredCandidate]`. نتیجهٔ هر فراخوانی مدل شناسهٔ ارائه‌دهنده/مدل و مصرف قابل گزارش را در `ProviderUsage` نگه می‌دارد؛ مصرف باید علاوه بر توکن‌های nullable، واحدهای صورتحساب سرویس مثل `search_units` را هم حفظ کند. هزینهٔ فاقد تعرفه یا مصرف ثبت‌شده، null است، نه صفر.

## هویت، نشست و مجوز

پیشنهاد نشست، یک شناسهٔ تصادفی با آنتروپی بالا در کوکی `HttpOnly`, `Secure` در HTTPS و `SameSite=Lax` است. فقط hash شناسه در جدول نشست نگهداری می‌شود؛ سرور در هر درخواست نشست منقضی‌نشده را پیدا می‌کند و نقش جاری را دوباره از رکورد کاربر می‌خواند. عمر نشست ۸ ساعت است؛ شناسه پس از ورود چرخانده می‌شود و خروج آن را باطل می‌کند. ورود با گذرواژهٔ hashشده با Argon2id از راه `pwdlib` انجام می‌شود. دو حساب نمونه (`employee`, `manager`) فقط از seed/CLI و ورودی محیطیِ محلی ساخته می‌شوند؛ ثبت‌نام عمومی، بازیابی گذرواژه و ارتقای مدیر از UI وجود ندارد. سیاست قفل یا محدودسازی تلاش‌های ورود هنگام پیاده‌سازی پیکربندی می‌شود.

API نقش را از کوکی معتبر و پایگاه‌داده می‌گیرد. هدر یا پارامتر `role` از مرورگر قابل اعتماد نیست و Route Handler نباید چنین هدرهایی را به‌عنوان مجوز عبور دهد. endpointهای تغییردهنده از جمله ورود، علاوه بر SameSite، مبدأ `Origin` را با مبدأ مورد انتظار تطبیق می‌دهند و در درخواست مرورگری با Origin غایب یا نامنطبق fail closed می‌شوند. دسترسی مدیر به بارگذاری، تغییر سطح دسترسی و حذف در backend بررسی می‌شود؛ پنهان‌کردن دکمه در رابط کنترل امنیتی محسوب نمی‌شود.

برای هر درخواست پرسش، سرور در ابتدای کار هویت، نقش و دامنهٔ اسناد فعال/جاری/آماده را از پایگاه‌داده می‌سازد. همان دامنه به تمام مرحله‌های lexical، vector، ادغام، rerank، زمینهٔ مدل و منابع خروجی داده می‌شود. پیش از بازگرداندن پاسخ کامل، وضعیت سندها و مجوز کاربر دوباره بررسی می‌شوند؛ اگر دسترسی یا نسخه در طول درخواست تغییر کرده باشد، خروجی وابسته به دادهٔ منسوخ تحویل نمی‌شود. این بررسی نمی‌تواند متنی را که پیش‌تر در زمان مجاز به ارائه‌دهندهٔ بیرونی فرستاده شده پس بگیرد؛ بنابراین فقط دادهٔ مجاز در لحظهٔ فراخوانی ارسال می‌شود. پاسخ‌ها stream نمی‌شوند تا بررسی نهایی پیش از تحویل کامل ممکن بماند.

## APIهای پیشنهادی

تمام مسیرهای داخلی FastAPI پشت پراکسی same-origin قرار می‌گیرند. مسیر `/api` بدون پیشوندگذاری دوباره تا upstream هدایت می‌شود. شکل دقیق schema پس از تثبیت رابط انتخاب می‌شود؛ جدول زیر قرارداد سطح بالا را نشان می‌دهد.

| مسیر | دسترسی | کارکرد |
|---|---|---|
| `POST /api/auth/login` | عمومی | اعتبارسنجی حساب و ایجاد نشست |
| `POST /api/auth/logout` | نشست معتبر | ابطال نشست جاری |
| `GET /api/auth/me` | نشست معتبر | دریافت شناسهٔ نمایشی و نقش جاری |
| `POST /api/answers` | کارمند و مدیر | پرسش و پاسخ کامل همراه با استنادهای مجاز یا امتناع |
| `GET /api/documents` | کارمند و مدیر | فهرست فقط اسناد فعال، آماده و مجاز همان نقش؛ شمار و فرادادهٔ اسناد نامجاز بازگردانده نمی‌شود |
| `GET /api/sources/{document_id}/sections/{section_id}?revision={revision}` | طبق مجوز جاری | دریافت متن همان بخش از revision ارجاع‌شده پس از بررسی مجدد دسترسی و نسخه؛ برای منبع ناموجود و غیرمجاز پاسخ عمومی یکسان 404 |
| `GET /api/manager/documents` | مدیر | فهرست اسناد و وضعیت پردازش |
| `POST /api/manager/documents` | مدیر | بارگذاری و ایجاد کار پردازش |
| `PUT /api/manager/documents/{document_id}` | مدیر | ساخت نسخهٔ جایگزین و فعال‌سازی اتمی پس از آماده‌شدن |
| `DELETE /api/manager/documents/{document_id}` | مدیر | خارج‌کردن فوری سند و داده‌های مشتق‌شده از جست‌وجو |
| `GET /api/manager/jobs/{job_id}` | مدیر | مشاهدهٔ وضعیت و خطای عملیاتی غیرحساس پردازش |

پیشنهاد اولیهٔ اعتبارسنجی بارگذاری: فقط `.md` و `.txt`، سقف 1 MiB برای هر فایل، سقف 100 سند فعال و سقف 2000 chunk جاریِ نمایه‌شده در کل. پرسش حداکثر 2000 نویسه است. بعد از parsing تعداد chunk محاسبه و پیش از هر فراخوانی provider سهمیه بررسی می‌شود؛ هنگام جایگزینی، chunkهای نسخهٔ جاری همان سند از محاسبهٔ سهمیه کم می‌شوند تا جایگزینی هم‌اندازه رد نشود. خطای سهمیه با پیام قابل اقدام به مدیر برمی‌گردد. این‌ها حدهای پیشنهادی قابل تنظیم‌اند. ورودی سند نامعتبر یا با سطح دسترسی نامعلوم رد می‌شود و هرگز به‌طور پیش‌فرض عمومی نمی‌شود.

## مدل دادهٔ پیشنهادی

شناسه‌های داخلی و خارجی جدا هستند: `chunk_id` برای ذخیره‌سازی و بازیابی داخلی است؛ استناد کاربر فقط با `document_id` و `section_id` پایدار ساخته می‌شود. فرادادهٔ پرسش و پاسخ هیچ‌گاه مجوز تعیین نمی‌کند.

| جدول | داده‌های اصلی |
|---|---|
| `users` | `id`, شناسهٔ ورود، `role` (`employee`/`manager`), وضعیت فعال و زمان ایجاد |
| `sessions` | hash شناسهٔ نشست، `user_id`, انقضای ۸ ساعته، ابطال و زمان ایجاد |
| `documents` | `document_id`, عنوان، `access_role`, نسخهٔ جاری، وضعیت محتوایی فعال/غیرفعال و زمان تغییر |
| `ingestion_jobs` | سند و نسخهٔ هدف، وضعیت `pending/indexing/ready/failed`, lease، شمارهٔ تلاش، خطای غیرحساس و زمان‌ها |
| `sections` | `document_id`, `revision`, `section_id` پایدار، ترتیب، عنوان/مسیر عنوان و متن اصلی بخش |
| `chunks` | `chunk_id`, سند/نسخه/بخش، متن قطعه، فرادادهٔ جست‌وجو و embedding با ابعاد منطبق بر مدل تنظیم‌شده |
| `request_runs` | شناسهٔ اجرا، زمان/مدت، نتیجه، شناسهٔ کاربر داخلی، پارامترهای پیکربندی و شناسه‌های نامزدهای بازیابی/رتبه؛ بدون متن خام پرسش یا prompt |

فهرست‌ها و joinها باید روی سند، نسخه، وضعیت، نقش، `section_id` و ارتباط chunk تنظیم شوند. بردارها در همان PostgreSQL ذخیره می‌شوند. با corpus فعلی کوچک، جست‌وجوی برداری می‌تواند روی حداکثر حدود ۸۰ بخش مجاز اسکن دقیق انجام دهد؛ ساخت ANN در این اندازه پیچیدگی اضافه می‌کند. اگر تعداد قطعه‌ها رشد کرد، تصمیم index و کارایی با اندازه‌گیری بازبینی می‌شود. ابعاد بردار و مدل embedding باید بین قطعه‌های یک index سازگار باشند؛ تغییر مدل نیازمند آماده‌سازی نمایهٔ تازه و جابه‌جایی اتمی است.

قرارداد دامنهٔ پیشنهادی برای هم‌راستایی ماژول‌ها: `Actor(user_id, role, session_id)`، `SourceRef(document_id, section_id, revision)`، `ChunkRecord(chunk_id, document_id, revision, section_id, text, access_role, ordinal)`، `RetrievalHit(chunk, lexical_rank, vector_rank, fused_score, rerank_score)`، `Claim(text, quote, source_refs)`، `ProviderUsage(provider, model, input_tokens, output_tokens, cost)` و `AnswerResult(answer, claims, sources, abstained, retrieval_hits, usage)`. ارجاع خروجی نسخهٔ مورد استناد را pin می‌کند؛ دسترسی همان revision پیش از نمایش بخش دوباره بررسی می‌شود. فهرست خطاها و nullable بودن امتیاز/مصرف باید در schema زمان پیاده‌سازی تثبیت شود.

امضاهای اصلی پیشنهادی سرویس‌ها: `resolve_actor(session_cookie) -> Actor|None`; `stage_upload(actor, file, metadata: UploadInput) -> IngestionJob`; `process_next_job() -> bool`; `list_documents(actor) -> list[DocumentSummary]`; `read_section(actor, SourceRef) -> SectionView`; `replace_document(actor, document_id, file, metadata: UploadInput) -> IngestionJob`; `delete_document(actor, document_id) -> None`; `retrieve(actor, question, config) -> list[RetrievalHit]`; `answer(actor, question, config) -> AnswerResult`. `UploadInput` عنوان و نقش دسترسیِ بازبینی‌شده توسط مدیر را دارد؛ نقش واقعی مدیر از نشست می‌آید و front matter فایل حق تغییر نقش کاربر ندارد. سرویس سند و بازیابی مجوز را خودشان بررسی می‌کنند، حتی اگر route قبلاً بررسی کرده باشد.

واردکردن corpus اولیه، مسیر CLI مدیریتیِ مجزایی دارد که شناسه‌های ثابت seed را حفظ می‌کند؛ بارگذاری جدید از رابط شناسهٔ تازهٔ سرور می‌گیرد. این CLI ورودی seed را اعتبارسنجی می‌کند، ولی هیچ مسیر عمومی برای انتخاب شناسهٔ سند مدیریتی از طرف کارمند ایجاد نمی‌کند.

تقسیم فایل پیشنهادی: `apps/web/` برای Next.js و پراکسی Route Handler؛ `apps/api/app/domain/models.py`, `auth/service.py`, `documents/service.py`, `retrieval/service.py`, `answer/service.py`, `providers/{embedding,generation,reranking}.py`, `api/{auth,answers,sources,manager}.py`, `cli/` و `evaluation/`. فایل‌های `.env` محلی و `.env.example` در ریشه؛ اجرای اولیه روی میزبان است، migrationهای SQLAlchemy/Alembic زیر `apps/api/alembic/`; فایل `.env` محلی از کنترل نسخه خارج می‌ماند.

## ورود، پردازش و جایگزینی سند

1. مدیر فایل را می‌فرستد. backend پسوند/محتوا، اندازه، متن UTF-8 قابل خواندن و فرادادهٔ لازم را بررسی می‌کند؛ شناسهٔ سند تازه را سرور تولید می‌کند. متن منبع در DB مرحلهٔ staging نگهداری می‌شود؛ فایل خام جداگانه روی دیسک باقی نمی‌ماند.
2. رکورد job در `pending` ثبت می‌شود. یک worker داخل سرویس API آن را با lease ۱۲۰ ثانیه‌ای برمی‌دارد و هر ۳۰ ثانیه تمدید می‌کند؛ lease منقضی‌شده پس از restart قابل بازیابی است. هر job حداکثر ۳ تلاش دارد.
3. متن اصلی و مرز عنوان‌ها حفظ می‌شوند. متن جست‌وجو نسخهٔ نرمال‌شدهٔ جداگانه دارد. هر بخش پاسخ‌پذیر بر اساس مرزهای عنوان تقسیم می‌شود؛ قطعه‌ها هم‌زمان حداکثر ۱۲۰۰ نویسه و ۴۰۰ توکن با prefix دارند؛ شمارش با tokenizer منطبق با مدل است. هم‌پوشانی تا ۱۵۰ نویسه فقط درون همان بخش و در بودجهٔ توکن مجاز است. یک قطعه هرگز از `section_id` مرجعش عبور نمی‌کند. شناسهٔ بخش هنگام جایگزینی تا حد امکان حفظ می‌شود و `chunk_id` جدا تولید می‌شود.
4. بعد از parsing، سقف ۲۰۰۰ chunk و سقف سند/فایل بررسی می‌شوند؛ اگر سهمیه رد شود، هیچ provider فراخوانی نمی‌شود. برای قطعه‌های نسخهٔ هدف embedding تولید و دادهٔ مشتق‌شده در وضعیت staging نوشته می‌شود. خطای parsing دائمی است؛ خطاهای موقت provider/job حداکثر تا سقف سه تلاش retry می‌شوند و سپس `failed` می‌شوند. دلیل قابل اقدام اما غیرحساس به مدیر نشان داده می‌شود.
5. پس از آماده‌شدن همهٔ قطعه‌ها و بردارها، تراکنش فعال‌سازی نسخهٔ جدید را جاری می‌کند و نسخهٔ قبلی را از جست‌وجو خارج می‌سازد. اگر جایگزینی شکست بخورد، نسخهٔ جاری قبلی می‌ماند.
6. کاهش مجوز، غیرفعال‌سازی یا حذف فوراً سند جاری و تمام مشتق‌ها را از query مجاز خارج می‌کند؛ حذف مجوز تازه به نسخهٔ قدیمی نمی‌دهد. واکشی منبع و بررسی نهایی پاسخ نیز مجوز جاری را دوباره می‌سنجد.

پردازش worker در نسخهٔ اول یک‌نمونه‌ای و بدون صف بیرونی است. قفل job/lease و بررسی مالکیت lease پیش از commit، مانع انتشار دوبارهٔ نتیجه در restart می‌شوند؛ کارگر قدیمی پس از از دست دادن lease حق فعال‌سازی نسخه را ندارد. فراخوانی بیرونی که پیش از قطع فرایند انجام شده ممکن است دوباره اجرا و هزینه‌دار شود، پس مصرف تلاش‌های تکراری باید ثبت شود. در رشد نیاز عملیاتی، صف مستقل تصمیم جداگانه‌ای خواهد بود؛ در این طرح جزء پیش‌فرض نیست.

### زمان‌بندی و retry ارائه‌دهنده

درخواست پاسخ سقف کلی ۶۰ ثانیه دارد؛ تلاش تولید حداکثر ۳۰ ثانیه، embedding پرسش ۱۰ ثانیه، و rerank ده ثانیه است. هر فراخوانی embedding/rerank حداکثر دو تلاش دارد؛ تولید در مجموع حداکثر دو تلاش، شامل retry یا اصلاح خروجی، دارد. همهٔ این تلاش‌ها باید در مهلت مشترک ۶۰ثانیه‌ای درخواست تمام شوند. خطاهای شبکه و statusهای 429، 502، 503 و 504 با backoff نمایی و jitter، تنها در محدودهٔ مهلت کلی retry می‌شوند. JSON نامعتبر حداکثر یک بار در همان سقف دو تلاش تولید دوباره خواسته می‌شود؛ retry شبکه و اصلاح JSON سهمیه‌های جدا نیستند. خطای نهایی یا اتمام مهلت، پاسخ سیاستی حدسی تولید نمی‌کند. provider جایگزین به‌صورت پنهان انتخاب نمی‌شود؛ هر تغییر مدل باید در پیکربندی و گزارش ارزیابی دیده شود.

## جست‌وجوی ترکیبی و پاسخ

### نرمال‌سازی و نامزدها

متن اصلی سند و پرسش برای نمایش/استناد حفظ می‌شوند. تابع نرمال‌سازی جست‌وجو نسخهٔ مشتق می‌سازد: ی/ي و ک/ك همسان، رقم‌های فارسی/عربی/لاتین هم‌ارز، فاصله و نیم‌فاصله (`ZWNJ`) یکدست، و نویسه‌های کنترلی/فاصله‌های تکراری اصلاح می‌شوند. نرمال‌سازی فقط روی رشتهٔ جست‌وجو اعمال می‌شود و متن ارجاع‌شده را بازنویسی نمی‌کند.

پس از ساخت دامنهٔ مجاز سمت سرور، دو مسیر موازی اجرا می‌شوند:

- **واژگانی:** در هر درخواست BM25 با `rank_bm25` تنها روی متن قطعه‌های فعال، جاری، آماده و مجاز که از DB همان درخواست خوانده شده‌اند محاسبه می‌شود. index سراسری یا cache مشترک BM25 برای نقش‌ها ساخته نمی‌شود. ۲۰ نامزد اول واژگانی نگه داشته می‌شوند.
- **معنایی:** embedding پرسش با adapter تنظیم‌شده ساخته و با بردارهای همان دامنه مقایسه می‌شود؛ برای اندازهٔ فعلی، اسکن دقیق PostgreSQL/pgvector کافی است. ۲۰ نامزد اول برداری نگه داشته می‌شوند.
- **ادغام:** اجتماع دو مسیر، حداکثر ۴۰ candidate یکتا دارد. رتبه‌ها با Reciprocal Rank Fusion و `k=60` ادغام می‌شوند؛ سپس حداکثر ۲۰ نتیجه به مرحلهٔ بعد می‌رود.
- **بازرتبه‌بندی اختیاری:** adapter بازرتبه‌بندی فقط پرسش و حداکثر همین ۲۰ نامزد مجاز را دریافت می‌کند. نبود/خطای provider به پاسخ حدسی منجر نمی‌شود؛ خطا به‌صورت شکست موقت مدیریت می‌شود یا در پیکربندی ارزیابی بدون rerank اجرا می‌شود.
- **زمینه:** حداکثر ۵ بخش/قطعهٔ برترِ مجاز برای ساخت پاسخ انتخاب می‌شوند. اگر یک بخش چند قطعه داشته باشد، خروجی ارزیابی همچنان رتبه و شناسهٔ هر chunk را نگه می‌دارد تا محاسبهٔ Recall@5 و MRR با قرارداد راهنمای ارزیابی سازگار باشد. هر سقف توکن یا ادغام قطعه باید در پیکربندی ثبت شود.

ارزیابی، سه پیکربندی را قابل مقایسه نگه می‌دارد: بازیاب برداری تنها به‌عنوان آزمایش افزوده، بازیابی ترکیبی بدون reranker به‌عنوان خط مبنای اصلی طرح، و همان بازیابی ترکیبی با reranker. هر سه روی نسخهٔ یکسان corpus/معیار، با فیلتر مجوز یکسان و تنظیمات ثبت‌شده اجرا می‌شوند. در نتیجهٔ ارزیابی باید هم رتبهٔ نامزدها و هم فهرست قابل مشاهده/فرستاده‌شده به مدل ثبت شود؛ شناسه یا متن سند غیرمجاز در هیچ‌یک وارد نمی‌شود.

### ساخت پاسخ و استناد

مدل پاسخ فقط پرسش و شواهد مجاز را می‌گیرد. دستور سامانه می‌خواهد هر ادعای سیاستی را به دست‌کم یک `SourceRef` از شواهد ارسالی متصل کند، برای هر ادعا نقل‌قول دقیق ارائه دهد، تضاد/ابهام را اعلام کند و در نبود شواهد کافی از پاسخ خودداری کند. خروجی JSON شامل `Claim(text, quote, source_refs)` و ارجاع به `document_id`, `section_id` و revision است. backend کل payload را اعتبارسنجی می‌کند: هر ادعا باید حداقل یک ارجاع معتبر از شواهد مجاز داشته باشد و نقل‌قول آن باید دقیقاً در متن بخش ارجاع‌شده وجود داشته باشد. اگر یک ادعا ارجاع ندارد، شناسه نامعتبر/غیرمجاز است، یا نقل‌قول تطبیق نمی‌کند، کل پاسخ رد می‌شود؛ ارجاع حذف نمی‌شود تا متن ادعای بی‌پشتوانه باقی بماند. یک درخواست اصلاح محدود در سقف دو تلاش تولید مجاز است و اگر اعتبارسنجی بار دوم شکست بخورد، خروجی امتناع خنثی است. پیش از بازگرداندن پاسخ معتبر نیز مجوز و revision جاری دوباره بررسی می‌شوند.

تطبیق شناسه و نقل‌قول فقط صحت ساختاری/لفظی ارجاع را می‌سنجد و استلزام معنایی یا درستی سیاستی ادعا را ثابت نمی‌کند. پوشش `required_facts`، پشتیبانی ادعاها، تعارض سند و خودداری باید طبق ارزیابی انسانی بررسی شود. وقتی سرویس بازیابی/تولید در دسترس نیست، پاسخ سیاستی ساخته نمی‌شود؛ خطای موقت عمومی نمایش داده می‌شود.

برای بخش بی‌پاسخ، مدل فقط یکی از enumهای `insufficient_evidence`, `ambiguous`, `conflict` را برمی‌گرداند؛ متن امتناع از عبارت ثابت سمت سرور ساخته می‌شود و رشتهٔ آزاد مدل در آن راه ندارد.

متن نمایشی پاسخ در سرور از ادعاهای اعتبارسنجی‌شده و عبارت‌های ثابتِ خودداری یا نبود شواهد ساخته می‌شود. فیلد نثر آزاد `answer` از خروجی مدل، اگر وجود داشته باشد، مستقیماً نمایش داده نمی‌شود؛ در غیر این صورت مدل می‌تواند با ارجاع‌های ظاهراً درست، ادعای اضافی را بیرون از فهرست claims وارد پاسخ کند. نقل‌قول باید در متن همان chunkهای ارسال‌شده به مدل وجود داشته باشد، نه فقط در بخشی از سند که مدل دریافت نکرده است.

`AnswerResult` نتیجهٔ داخلی است و می‌تواند اطلاعات retrieval و مصرف را برای ارزیابی نگه دارد. پاسخ عمومی `/api/answers` فقط `request_id`, `answer`, `claims`, `sources`, `abstained` دارد؛ متن chunkها، امتیازهای داخلی و جزئیات مدل/مصرف جزو رابط کاربر نیستند. نتایج تفصیلی ارزیابی فقط در artifact محلی با دسترسی محدود ثبت می‌شوند.

## حریم داده و ثبت اجرا

پایگاه‌داده و فایل‌های محیطی محلی باید خارج از کنترل نسخه باشند. کلیدها و رمزهای ارائه‌دهندگان فقط از متغیر محیطی/مدیر اسرار استقرار خوانده می‌شوند و در رابط، لاگ یا خطای API برگردانده نمی‌شوند. لاگ عملیاتی شامل شناسهٔ اجرا، زمان‌ها، وضعیت، نسخهٔ index، نام/نسخهٔ مدل و شناسه/رتبهٔ candidateهای مجاز است؛ متن خام پرسش، پاسخ، prompt یا محتوا در `request_runs` ذخیره نمی‌شود.

راهنمای ارزیابی، ذخیرهٔ پاسخ و شواهد بازیابی برای تحلیل آفلاین را می‌خواهد. این داده‌ها در artifact اجرای ارزیابی و با دسترسی محدود نگهداری می‌شوند، نه در جدول اجراهای معمول محصول؛ معیار شامل پرسش‌های ساختگی است، اما خروجی اجرا همچنان باید حفاظت شود. شناسه‌های اسناد ممنوعهٔ مجموعهٔ ارزیابی هرگز به نقش نامجاز، درخواست مدل یا پاسخ ارزیابی زنده تزریق نمی‌شوند. هر ثبت متن/نگهداری بلندمدت در محصول نیازمند تصمیم سیاستی جداگانه است.

## پیکربندی و ارزیابی

پیکربندی هر اجرا دست‌کم نسخهٔ کد، نسخه/hash corpus، نسخهٔ معیار، provider و شناسه/نسخهٔ مدل برای تولید/embedding/rerank، نسخهٔ prompt، تنظیمات تولید، روش retrieval، اندازهٔ candidate/top-k، `k` در RRF، آستانهٔ خودداری و فیلترهای دسترسی را ثبت می‌کند. شناسهٔ راز ثبت نمی‌شود. retry، خطا و زمان کل درخواست نیز شمرده می‌شود؛ هزینه بر پایهٔ مصرف ثبت‌شده و تعرفهٔ تاریخ‌دار گزارش می‌شود و برای جزء فاقد داده «ثبت‌نشده» می‌آید، نه صفر. پیش‌فرض‌های آغازین شامل embedding 768 بُعدی، 20 نامزد در هر مسیر، RRF `k=60`, حداکثر 20 نامزد برای rerank و top-5 نهایی است؛ این تنظیم‌ها قبل از ادعای کیفیت با مجموعهٔ توسعه تنظیم و در هر گزارش عیناً ثبت می‌شوند.

۴۰ سؤال موجود معیار ثابت است و برای تنظیم مکرر استفاده نمی‌شود. تنظیمات و prompt ابتدا با مجموعهٔ توسعهٔ جداگانه بررسی می‌شوند. گزارش معیار ثابت باید Recall@5 و MRR روی جفت‌های `(document_id, section_id)`، تکمیل حقایق و رفتار امتناع، پشتیبانی استناد، موارد نشت مشاهده‌شده، تأخیر p50/p95 و هزینه را مطابق [راهنمای ارزیابی](../evaluation-guide.md) تفکیک کند. نتیجهٔ صفر نشت فقط به اجراهای ثبت‌شده مربوط است و تضمین امنیت کلی نیست.

## پیش‌فرض‌های نهایی برای بررسی هنگام پیاده‌سازی

این سند پیش‌فرض‌های اجرایی را مشخص کرده تا پیاده‌سازی بعدی بر قرارداد روشن تکیه کند. مواردی که هنوز دادهٔ لازم برای تثبیت ندارند، سیاست محتوایی‌اند و باید با نتیجهٔ ارزیابی توسعه تعیین شوند:

- آستانهٔ عددیِ خودداری یا حد کیفیت ادعا نمی‌شود؛ معیار مناسب با مجموعهٔ توسعه تنظیم می‌شود و در مجموعهٔ ۴۰تایی ثابت تنظیم مکرر صورت نمی‌گیرد.
- اگر اسناد منبع با هم تعارض داشته باشند، پاسخ از انتخاب خودسرانه پرهیز و تعارض را با استنادهای مجاز گزارش می‌کند.
- provider/model و تنظیم‌های آغازین در بخش‌های بالا پیشنهاد شده‌اند؛ availability، structured output، مدت پاسخ، مصرف و کیفیت روی endpointهای واقعی باید پیش از اتکا smoke-test و اندازه‌گیری شوند. هیچ نتیجهٔ چنین آزمایشی در این سند گزارش نمی‌شود.
- پاک‌سازی فیزیکی نسخه‌های قدیمی، backup/restore، نگهداری بلندمدت telemetry و ظرفیت اجرای واقعی پیش از استقرار نهایی عملیاتی می‌شوند؛ از دامنهٔ نسخهٔ اول، نسخه‌بندی پیشرفته و استقرار توزیع‌شده خارج است.
- اگر حجم از 100 سند یا 2000 chunk عبور کند یا latency اندازه‌گیری‌شده نامناسب باشد، سقف‌ها و راهبرد index/صف با دادهٔ جدید بازبینی می‌شوند؛ ANN، صف جداگانه و workerهای موازی پیش‌فرض این نسخه نیستند.
