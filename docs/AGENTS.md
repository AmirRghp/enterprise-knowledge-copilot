# دستورهای عامل کدنویسی هوش مصنوعی

## 1. زمینهٔ پروژه

پروژه «دستیار دانش سازمانی سپهر داده» برای پاسخ فارسی مستند از corpus ساختگی و دو نقش `employee` و `manager` برنامه‌ریزی شده است. این checkout در مرحلهٔ مستندسازی است؛ برنامه و API هنوز scaffold نشده‌اند.

## 2. مرجع تصمیم

پیش از هر تغییر معنادار، سند مرتبط را بخوانید:

- `docs/PRD.md` — محصول و دامنه
- `docs/DESIGN_SYSTEM.md` — قواعد Notion و RTL
- `docs/ARCHITECTURE.md` — معماری و قراردادهای سرویس
- `docs/DATABASE.md` — schema، پایگاه مستقل و migration
- `docs/SECURITY.md` — امنیت و مجوز
- `docs/CODE_STYLE.md` — قرارداد کد
- `docs/TESTING.md` — معیار اعتبارسنجی

اسناد تکمیلی: `docs/evaluation-guide.md`، `docs/corpus-index.md`، `corpus/` و `eval/questions.jsonl`. هفت سند اصلی بالا مرجع تصمیم‌های جاری‌اند. `docs/archive/` فقط سابقه است و مرجع اجرایی یا دستور کار محسوب نمی‌شود.
سند طراحی پیشنهاد است؛ فرضیه را واقعیت یا رفتار پیاده‌شده جلوه ندهید. اگر تصمیم تازه با آن تعارض دارد، تعارض را مشخص و سند مسئول را به‌روز کنید.

## 3. قواعد عمومی

- کارهای Git به عامل اختصاصی `git_manager` سپرده شوند؛ commit و push فقط با مجوز کاربر، با حفظ تاریخچهٔ remote و بدون stage کردن `.env` انجام شوند.

- قبل از تغییر، وضعیت Git و فایل‌های واقعاً موجود را بررسی کنید؛ ساختار پیشنهادی را با برنامهٔ اجراشده اشتباه نگیرید.
- هیچ پیاده‌سازی برنامه‌ای را در مرحلهٔ مستندسازی آغاز نکنید مگر درخواست کار صریحاً دامنه را عوض کند.
- تغییر را محدود نگه دارید؛ secret، دادهٔ واقعی یا سند مدیریتی را افشا نکنید.
- پایگاه هدف پروژه PostgreSQL 16 موجود `rag-postgres` با host port `5433` است. فقط پایگاه اختصاصی `enterprise_knowledge_copilot` هدف آینده است؛ این DB هنوز ساخته نشده و migration ندارد.
- container، volume یا دادهٔ قدیمی `rag-postgres` را حذف، reset یا بازسازی نکنید. هیچ DB container تازه‌ای نسازید.
- embedding محلی پیش‌فرض Ollama (`nomic-embed-text-v2-moe:latest`، ۷۶۸ بُعد، `localhost:11434`) است. تولید از OpenRouter با کلید خصوصی و خالی فعلی پیکربندی می‌شود. Cohere rerank اختیاری و پیش‌فرض خاموش است.
- اسناد خارجی/نمونه‌ای که فقط برای مرجع داده شده‌اند، وظیفهٔ پیاده‌سازی اضافه ایجاد نمی‌کنند.

## 4. برنامه‌ریزی

برای کار غیرساده:

1. نیاز و فایل‌های موجود را بررسی کنید.
2. سندهای مربوط و مرز تغییر را مشخص کنید.
3. اثر روی دسترسی، داده، provider، migration و آزمون را یادداشت کنید.
4. اگر ابهام تصمیم‌ساز یا تعارض وجود دارد، قبل از حدس‌زدن آن را گزارش کنید.

کارهای ساده و نگارش اسناد طبق درخواست کاربر به `gpt-6-luna` سپرده شوند؛ عامل اصلی تصمیم فنی، امنیت، سازگاری و خروجی نهایی را بازبینی کند.

## 5. پیاده‌سازی

- قرارداد مجوز را در backend نگه دارید؛ فیلتر نهایی پاسخ جای فیلتر retrieval نیست.
- متن پرسش و سند را دادهٔ نامطمئن بدانید؛ نقش از نشست معتبر سمت سرور می‌آید.
- برای پاسخ، استناد پایدار `document_id`/`section_id` و تطبیق نقل‌قول را اعتبارسنجی کنید.
- تغییر پایگاه با migration افزایشی و فقط روی DB اختصاصی پروژه انجام شود.
- providerها پشت interface بمانند؛ fallback پنهانی یا ارسال دادهٔ غیرمجاز به سرویس بیرونی اضافه نکنید.

## 6. اعتبارسنجی

- فقط فرمان‌هایی را اجرا کنید که manifest و scaffold موجود تأیید می‌کنند؛ اکنون برنامه‌ای برای lint/build/test وجود ندارد.
- آزمون‌های آینده باید شکست مجوز، رقابت و fencing lease، اعتبار استناد و نقل‌قول، محدودیت token و lifecycle سند را پوشش دهند.
- ارزیابی ثابت ۴۰ نمونه‌ای را برای تنظیم مکرر استفاده نکنید؛ کیفیت معنایی را با بازبینی انسانی بسنجید.
- پیش از گزارش اتمام، diff و فایل‌های تغییرکرده را بازبینی و نتیجهٔ اجرا را دقیق بیان کنید. آزمون اجرا‌نشده را موفق گزارش نکنید.

## 7. مستندات

هرگاه رفتار محصول، معماری، schema، API، امنیت یا فرمان‌های واقعی تغییر کرد، سند مربوط را همان‌جا به‌روز کنید. فرض‌های پیشنهادی و وضعیت پیاده‌سازی‌نشده را برچسب بزنید.

## 8. رسیدگی به تعارض

اگر نیاز محصول، سند یا وضعیت واقعی محیط ناسازگار است، فایل/تصمیم متعارض را نام ببرید و بخش مستقل کار را ادامه دهید. برای موردی که مجوز داده یا امنیت را تغییر می‌دهد حدس نزنید.

## 9. معیار اتمام

- درخواست در محدودهٔ مجاز تکمیل و مستندات مربوط به‌روز شده باشد.
- تغییر ناخواسته یا اثر روی دادهٔ قدیمی وجود نداشته باشد.
- آزمون و build فقط در صورت وجود و اجرا گزارش شوند؛ مرحلهٔ مستندسازی فعلی ادعای اجرای برنامه یا آزمون ندارد.
