# راهنمای امنیت

## 1. احراز هویت

**وضعیت:** احراز هویت، نشست، محدودسازی login و proxy هم‌مبدأ پیاده شده‌اند. موارد زیر با برچسب «پیاده‌شده» رفتار فعلی‌اند؛ پیشنهادها و محدودیت‌های باقی‌مانده صریحاً مشخص شده‌اند. تاریخچهٔ انتشار در [برنامهٔ اجرا](plans/plans.md) است.

Setup و فرم ساخت/ویرایش نام و نام خانوادگی trimشده، غیرخالی و حداکثر ۱۰۰ نویسه می‌گیرند. فیلدهای نام در migration `0006` nullable هستند تا برای کاربران قدیمیِ ناشناخته NULL بمانند؛ پاسخ فهرست مدیر آن‌ها را nullable می‌دهد و UI در نبود نام login را نمایش می‌دهد. مدیر پنل کاربر را با dialog بومی اداره می‌کند. تغییر ایمیل، نقش، فعال‌بودن یا گذرواژه نشست‌های هدف را باطل می‌کند؛ تغییر نام به‌تنهایی نشست را حفظ می‌کند. PATCH ایمیل، نام‌ها، نقش/وضعیت و گذرواژهٔ اختیاری را اتمیک ذخیره می‌کند؛ گذرواژهٔ خالی hash را حفظ می‌کند. ایمیل تکراری `409` می‌دهد و هیچ تغییری را اعمال نمی‌کند. آخرین مدیر فعال همچنان تحت رقابت هم‌زمان محافظت می‌شود.

مدیرها از مسیر same-origin `/manager/system-prompts` به کتابخانهٔ مشترک نصب دسترسی دارند. API دوباره نقش مدیر را بررسی می‌کند؛ فقط سازنده می‌تواند prompt سفارشی را ویرایش کند و prompt پیش‌فرض تغییرناپذیر است. ساخت، ویرایش فعال و فعال‌سازی با ورودی محدود، revision/version و قفل تراکنشی کنترل می‌شوند. محتوای prompt دادهٔ مدیر است، اما تضمین مجوز و شواهد نیست: قواعد ثابت سرور همیشه در ابتدای system message باقی می‌مانند و prompt سفارشی فقط به‌عنوان دستور تکمیلی فرستاده می‌شود. نبود یا ناسازگاری تنظیم پیش از تماس با مدل خطا می‌دهد. متن خام prompt در log و artifact ارزیابی ثبت نمی‌شود؛ artifact ارزیابی hash متن مؤثر ارسالی را ذخیره می‌کند.

در Part 5، صفحهٔ `/login` از proxy هم‌مبدأ استفاده می‌کند. Route Handler مسیرهای مجاز را به method/path محدود می‌کند: فقط `POST login/logout` و `GET me` و درخواست دارای query پذیرفته نیست. مقصدها از `API_BASE_URL` و `WEB_ORIGIN` سروری می‌آیند؛ environment بر مقادیر فایل `.env` ریشه اولویت دارد. پراکسی فقط کوکی `ekc_session` را به API می‌فرستد و Origin اعتبارسنجی‌شده را برای عملیات تغییردهنده می‌فرستد. بدنهٔ login فقط JSON تا ۸ KiB است؛ نقش، هویت و headerهای forwarding حذف می‌شوند و بدنهٔ اضافی به سرویس نمی‌رسد. خطاها عمومی‌اند، فراخوانی API مهلت ده‌ثانیه‌ای دارد و redirect دنبال نمی‌شود؛ پاسخ‌ها `no-store` هستند. کوکی پاسخ با ویژگی‌های `HttpOnly` و host-only عبور می‌کند. پاسخ‌های Next شامل `X-Content-Type-Options: nosniff`، `X-Frame-Options: DENY` و `Referrer-Policy: same-origin` هستند؛ این headerها و `no-store` بودن صفحهٔ ورود در مرورگر production بررسی شدند. بررسی‌های ثبت‌شدهٔ Part 5 موفق شدند و پارت منتشر شد. محدودکنندهٔ login در API بدون تغییر باقی مانده است؛ درخواست‌های مستقیم از پراکسی loopback در سهم IP مشترک محاسبه می‌شوند چون هدرهای forwarded قابل اعتماد نیستند.

روش جاری: هش گذرواژه با Argon2id؛ نشست opaque تصادفی و فقط hash آن در DB. کوکی `HttpOnly; SameSite=Lax`، در HTTPS برابر `Secure`، عمر ۸ ساعت؛ logout نشست را باطل و کوکی را حذف می‌کند. ورود موفق نشست ارسالی را همراه با صدور نشست تازه اتمی باطل می‌کند؛ نشست‌های دستگاه‌های دیگر دست‌نخورده می‌مانند. نقش و فعال‌بودن حساب در هر درخواست از DB خوانده می‌شوند. گزاره‌های قدیمی دربارهٔ seed حساب‌ها در سوابق Parts 4–5 تاریخی‌اند و با قرارداد Part 22 جایگزین می‌شوند.

مدیرها می‌توانند حساب بسازند، اما تغییر نقش یا غیرفعال‌سازی آخرین مدیر فعال رد می‌شود. این قاعده باید در پایگاه‌داده و زیر تراکنش سریال‌شده اجرا شود تا درخواست‌های هم‌زمان هر دو مدیر نهایی را حذف نکنند. تغییر ایمیل، نقش، غیرفعال‌سازی و تغییر گذرواژه همهٔ نشست‌های هدف را revoke می‌کند؛ ویرایش نام نشست‌ها را حفظ می‌کند.

## 2. مجوزدهی

- مجوز هر سند پیش از بازیابی و در تمام مراحل retrieval، rerank، تولید، استناد و نمایش بررسی شود.
- کارمند فقط اسناد عمومیِ فعال، جاری و آماده را ببیند؛ مدیر به آن‌ها و اسناد مدیریتی دسترسی دارد.
- عملیات بارگذاری، تغییر دسترسی و حذف فقط برای مدیر است و کنترل آن در backend انجام می‌شود.
- نقش ارسالی در متن، پارامتر یا header کاربر قابل اعتماد نیست. در پرسش ترکیبی، بخش عمومی را پاسخ دهید و دربارهٔ وجود یا جزئیات بخش غیرمجاز چیزی فاش نکنید.
- پیش از تحویل پاسخ و خواندن متن منبع، مجوز و نسخهٔ جاری دوباره بررسی شود.
- predicate مشترک retrieval باید نقش و فعال‌بودن فعلی را از DB بخواند؛ نقش یا وضعیت ذخیره‌شده در session مبنای مجوز نیست.
- گسترش دسترسی در جایگزینی فقط پس از فعال‌سازی revision تازه اعمال شود؛ نسخهٔ قدیمی نباید برای کاربران تازه‌مجازشده باز شود. کاهش دسترسی فوراً اعمال شود.

پارت ۱۰ این قاعده را در `apps/api/app/ingestion/store.py` پیاده کرد و دو نکته را صریح روشن کرد که پیش‌تر مبهم بود:

- **کاهش دسترسی در شکست جایگزینی برنمی‌گردد.** `documents.access_role` در همان تراکنشی که job ساخته می‌شود باریک‌تر می‌شود و اگر آن job ناموفق شود همین‌جا می‌ماند. این بده‌بستان آگاهانه است: اگر برگردانده شود، سیاست باریک‌شده فقط به اندازهٔ یک اجرای پردازش — چند ثانیه — دوام می‌آورد، یعنی دقیقاً همان پنجره‌ای که سند باید در آن از دسترس افرادی که مجازشان لغو شده خارج باشد. تنها چیزی که در شکست پاک می‌شود سیاست *اعمال‌نشده* است (`staged_access_role` و `staged_title`)، نه `access_role`. آزمون `test_a_narrowing_survives_a_failed_replacement` همین را نگه می‌دارد.
- **دو job هم‌زمان برای یک سند پذیرفته نمی‌شود.** `stage_replace` اگر هر job `pending` یا `indexing` برای آن سند ببیند `409` می‌دهد. این فقط دربارهٔ دو جایگزینی نیست: job خودِ create هم می‌آید، چون سندی که هنوز چیزی منتشر نکرده revision جایگزینی ندارد و دو job با مبنای `NULL` هر دو compare-and-swap را رد می‌کنند و هر دو روی هم منتشر می‌شوند. دو جایگزینی هم‌زمان هم `staged_*` یکدیگر را پاک می‌کردند.

هر دو مسیر staging و delete از قفل سند `documents` عبور می‌کنند، پس یکی از آن‌ها دیگری را کامل می‌بیند. حذف همچنین قفل مشورتی ناشر را اول می‌گیرد تا ترتیب قفلش با فعال‌سازی چرخه نسازد.

حذف سند در این سند بند جداگانه‌ای ندارد چون لازم نیست: حذف فقط `status` را `inactive` می‌کند و متن منتشرشده را نگه می‌دارد. آنچه در [پایگاه‌داده](DATABASE.md) آمده این است که delete هر job باز آن سند را ناموفق و lease آن را پاک می‌کند، پس هیچ worker در حال اجرایی نمی‌تواند سند حذف‌شده را با یک نوشتن دیرهنگام زنده کند؛ و فعال‌سازی هم سند `inactive` را رد می‌کند. اگر حذف به هر دلیلی پیش از رسیدن job به فعال‌سازی انجام نشده باشد، worker خودش job را با lease پاک‌شده به وضعیت terminal می‌رساند و سطرهای staging‌اش را می‌اندازد، پس job یتیم باقی نمی‌ماند.

مرزهای HTTP این دو endpoint هم در پارت ۱۰ صریح شد: شناسهٔ سند با الگوی `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$` پذیرفته می‌شود، پس هم `DOC-001` و هم UUID معتبرند و هیچ جداکننده یا escape از پروکسی عبور نمی‌کند؛ سند ناشناخته `404`، سند حذف‌شده یا job در جریان `409`، و کارمند یا Origin بیگانه `403`. `DELETE` برای شناسهٔ ناشناخته هم `204` می‌دهد تا retry و دوبار کلیک خطا نشوند. proxy وب هر دو متد را فقط روی یک سند مجاز می‌داند و `PUT` را مثل `POST` پیش از هرس بندی از نظر Origin و اندازه محدود می‌کند.

پارت ۱۱ allowlist بازیابی را به‌صورت **پیشوند SQL** پیاده کرد، در `apps/api/app/retrieval/store.py`. هر statement هر دو مسیر، شرط‌های `status = 'active'`، `current_revision IS NOT NULL`، وجود job `ready` برای همان revision و `access_role` مجاز را با هم حمل می‌کند. فیلتر پس از بازیابی رد شد چون شمار نتیجه را به اسناد غیرمجاز وابسته می‌کند و ایمنی را به فراموش‌نشدن یک فیلتر گردایده می‌سازد. شبکهٔ نقش در `app/domain/models.py` یک‌بار تعریف شده تا ingestion و retrieval نتوانند دربارهٔ «چه کسی چه می‌بیند» اختلاف پیدا کنند.

گزارش توسعهٔ retrieval (`app/cli/retrieval_report.py`) هیچ متن سندی چاپ نمی‌کند: نه متن قطعه، نه متن بخش، نه عنوان سند، نه خود پرسش. فقط شناسه‌ها، رتبه‌ها، نمرهٔ ادغام و نقشی که واقعاً اعمال شده. این گزارش اول چیزی است که در تیکت یا گفت‌وگو کپی می‌شود، و گزارش یک کارمند نباید حتی یک خط از سند مدیرمحور را حمل کند. نقش از ردیف `users` خوانده می‌شود، نه از آرگومان؛ CLI اصلاً پارامتر نقش ندارد.

نرمال‌سازی فارسی فقط روی متن مشتق جست‌وجو اعمال می‌شود: پرسش **یک‌بار** نرمال می‌شود و همان رشته به BM25 و provider داده می‌شود، و BM25 روی ستون `search_text` کار می‌کند. `chunk_text` که نقل‌قول استناد بعداً با آن تطبیق داده می‌شود دست‌نخورده می‌ماند.

**دو بار خواندن، یک‌بار تصمیم.** رتبه‌بندی روی snapshot است و رتبه‌بندی چیزی را از رتبه خارج نمی‌کند، پس candidateهای ادغام‌شده پیش از بازگرداندن یک‌بار دیگر زیر همان allowlist خوانده می‌شوند (`store.read_ranked_chunks`). آنچه دیگر مجاز نیست حذف می‌شود و متن hit از همین خواندن تازه می‌آید. یک candidate هرگز با chunk دیگری جایگزین نمی‌شود: اگر جایگزینی در میانه رخ داده باشد، ردیف‌های قدیم دیگر `revision = current_revision` را ندارند و در نتیجه غایب‌اند.

**متقاضی‌های ناسازگار fail-closed می‌شوند.** `store.assert_index_consistent` پیش از هر رتبه‌بندی، provider/مدل/digest/ابعاد ذخیره‌شدهٔ دامنهٔ مجاز را با providerی که بردار پرسش را ساخته می‌سنجد؛ digest مختلط، مدل یا ابعاد ناسازگار خطای امن می‌دهد و هیچ hitی برنمی‌گردد. این بررسی روی **دامنهٔ مجاز** اجرا می‌شود نه کل `chunks`، چون حکم سراسری در دسترس‌بودن یک کاربر را به ردیف‌های غیرمجاز وابسته می‌کرد. پیام خطا نام سند و digest مشاهده‌شده را لو نمی‌دهد.

**رفتار تاریخی پارت ۱۲:** اولین ارسال متن سند به سرویس بیرونی rerank بود و در آن پارت پیش‌فرض خاموش ماند. یک فراخوانی rerank پرسش کاربر و متن قطعه‌های نامزد را به OpenRouter می‌فرستاد. آن پیاده‌سازی با `RERANK_ENABLED=false` کار می‌کرد و `RERANK_ENABLED` را پیش از هر درخواست بررسی می‌کرد؛ در حالت خاموش نه adapter ساخته می‌شود، نه client، نه درخواستی — **صفر** کار provider، نه یک فراخوانی که زودهنگام برگردد. فقط corpus ساختگی و غیرشخصی پروژه روی endpoint رایگان مجاز است؛ دادهٔ واقعی یا شخصی پیش از بازبینی حریم خصوصی ممنوع است. مدل رایگان NVIDIA دادهٔ درخواست را برای امنیت و بهبود ثبت می‌کند.

**مجوز در مرحلهٔ خروج دوباره بررسی می‌شود، و این ادعا شامل تلاش‌های retry هم هست.** `store.read_ranked_chunks` — همان تابعی که دروازهٔ پایانی پارت ۱۱ است — پیش از هر ارسال دوباره صدا زده می‌شود، و `store.assert_chunks_consistent` روی همان ردیف‌های تازه اجرا می‌شود. این تنها نقطه‌ای است که داده از فرایند خارج می‌شود، پس تنها جایی که این بررسی معنا دارد؛ نوشتن predicate دوم یعنی دو منبع حقیقت که می‌توانند اختلاف پیدا کنند. payload از همین ردیف‌های تازه ساخته می‌شود، نه از متن hitهایی که خواندن fusion نگه داشته است، چون اگر revision یا متن سند عوض شده باشد متن hit قدیمی است.

**تلاش دوم بدنه را از نو می‌سازد.** بدنهٔ درخواست یک‌بار پیش از حلقهٔ retry ساخته نمی‌شود؛ خودِ `arun_with_retry` هر تلاش یک تازه‌ساز را صدا می‌زند و آن تازه‌ساز دوباره دروازهٔ مجوز را اجرا می‌کند. بدنهٔ آمادهٔ پیشین یعنی تلاش دوم متن تلاش اول را عیناً می‌فرستاد: اگر در فاصلهٔ backoff دسترسی لغو، سند حذف یا revision عوض می‌شد، متنی که فراخواننده دیگر حق خواندنش را نداشت بیرون می‌رفت. اگر تازه‌سازی خالی شود، درخواست fail-closed رد می‌شود و ارسال نمی‌شود — فرستادن فهرستی کوتاه‌تر بدتر بود، چون شمارش پاسخ با عددی سنجیده می‌شد که واقعاً فرستاده نشده بود.

**`index` یعنی جایگاه در فهرستی که واقعاً فرستاده شد، نه فهرست اولیه.** adapter فهرست و `top_n` مؤثر را همراه payload برمی‌گرداند و نگاشت با همان‌ها انجام می‌شود. اگر نگاشت علیه فهرست اولیه انجام شود، هر تلاشی که فهرست متفاوتی بفرستد نمرهٔ واقعی را به chunk اشتباه می‌چسباند؛ و اگر شمارش علیه درخواست اولیه باشد، پاسخِ درستِ provider به‌عنوان «۳ نتیجه برای ۴ درخواستی که نداده» رد می‌شود — شکستی کاذب روی سرویسی که دقیقاً همان را خواسته بود پاسخ داده بود.

**دروازهٔ خروج پیش از هر ارسال دوباره اجرا می‌شود، از جمله retry و repair.** آخرین بررسی مجوزِ `retrieve` **پیش از** فراخوانی generation رخ می‌دهد و برمی‌گردد؛ اگر در فاصلهٔ بازگشت آن تا درخواست provider، دسترسی تنگ شود، سند حذف شود یا revision جایگزین گردد، متن قدیمی هنوز روی سیم می‌رود. پس هر تلاش یک تازه‌ساز می‌گیرد که `read_ranked_chunks` را با actor اجرا می‌کند و `assert_chunks_consistent` را روی همان ردیف‌ها می‌سنجد. این دقیقاً همان دروازه‌ای است که پارت ۱۲ برای rerank ساخت و یک لایه بالاتر دوباره لازم شد. نکتهٔ مهم‌تر: **نوبت user هر تلاش از شواهد همان تلاش ساخته می‌شود** — یک‌بار ساختن آن یعنی متن منصرف‌شده در retry دوباره می‌رود در حالی که نگاشت فقط بازمانده را توصیف می‌کند. تازه‌سازی خالی fail-closed می‌شود.

**نبود شواهد مجاز خطای provider نیست و نباید چنین گزارش شود.** وقتی تازه‌سازی خالی برمی‌گردد، **هیچ درخواستی فرستاده نشده** — پس نه پاسخی وجود دارد که نامعتبر باشد و نه طرح‌واره‌ای که کسی رعایت نکرده باشد. به همین دلیل خطای جداگانهٔ `GenerationEvidenceError` دارد که **فوری متوقف می‌شود**: نه retry می‌خورد، نه repair. repair در این حالت یعنی خواستن دوبارهٔ همان پرسش با شواهدی که فراخواننده دیگر حق فرستادنش را ندارد — یعنی مصرف یک تلاش برای رسیدن به همان رد. نگاشت آن در گزارش `EXIT_NO_HITS` با پیام «شاهد مجازی برای تولید نبود» است، **نه** `EXIT_SCHEMA`؛ آن پیام به اپراتور می‌گوید endpoint طرح‌واره را رعایت نکرده و درستی می‌فرستد دنبال خرابی endpoint، حال آنکه سند فقط دیگر خواندنی نیست.

**دستگیره‌ها یک‌بار شماره می‌خورند و جابه‌جا نمی‌شوند.** دستگیره از ترتیب retrieval می‌آید و پس از حذف یک قطعه به قطعهٔ بعدی منتقل نمی‌شود: دستگیره‌ای که جای‌اش عوض شود بی‌سروصدا به قطعهٔ دیگری اشاره می‌کند و claimی که به آن ارجاع داده به سند غلط نگاشت می‌شود. فقط دستگیره‌هایی که **همان تلاش** فرستاده قابل ارجاع‌اند، پس تازه‌سازی که یکی را حذف کند باعث رد پاسخی می‌شود که به حذف‌شده ارجاع دارد.

**مصرف در مسیر خطا هم به اپراتور نشان داده می‌شود.** حسابداری نگه‌داشتن بی‌فایده است اگر کسی نبیندش: فرمانی که با کد غیرصفر خارج می‌شود و فقط یک دلیل چاپ می‌کند هیچ راهی به اپراتور نمی‌دهد که بفهمد تلاش رایگان بوده یا گران، و عدد با خروج فرایند از بین می‌رود. هر سه خروج خطای فرمان تولید یک خط پاک‌سازی‌شدهٔ مصرف روی stderr چاپ می‌کنند، و همین برای `preflight_generation` هم هست — با سقف روزانهٔ پنجاه درخواست، یک preflight ناموفق دقیقاً همان اجرایی است که هزینه‌اش را باید دید. این خط فقط عدد و نام دارد و `None` را به‌صورت `None` چاپ می‌کند نه صفر.

**نهایی‌سازی مصرف در `finally` است، نه در هر مسیر خروج.** فهرست مسیرهایی که حلقهٔ تلاش می‌تواند از آن‌ها خارج شود هر بار بزرگ‌تر می‌شود، و مسیر تازه یعنی مصرف فراخوانی‌هایی که واقعاً رخ داده‌اند بی‌سروصدا حذف می‌شود. همین اتفاق افتاد: یک پاسخ `503` صورتحساب‌شده که تازه‌سازی بعدی خالی شد، هزینه‌اش را از گزارش حذف کرد چون آن استثنا از هیچ‌کدام از دو محل نهایی‌سازی نمی‌گذشت. با `finally` هر مسیر خروج — از جمله استثنایی که بعداً اضافه شود — گزارش می‌کند چه چیزی خرج شده است.

**مصرف همهٔ تلاش‌ها گزارش می‌شود، نه فقط تلاش موفق.** پاسخی که نامعتبر بود باز هم تولید و باز هم صورتحسابی است؛ مجموعه‌کردن فقط تلاش موفق، هزینهٔ واقعی فراخوانی را کمتر از واقع نشان می‌داد. توکن‌ها دقیقاً جمع می‌شوند، و **رقمی که هر تلاش گزارش نکرده، مجموعه را نامشخص می‌کند نه صفر** — چون صفر یعنی «رایگان بود» و این ادعایی است دربارهٔ پولی که کسی نکرده. درخواستی که اصلاً به provider نرسید چیزی ثبت نمی‌کند، چون هزینه‌ای قابل نسبت‌دادن ندارد. `attempts` در `ProviderUsage` تعداد فراخوانی‌ها را می‌گوید تا گزارش نشان دهد عددِ بالای یک یعنی retry یا repair رخ داده و هزینه‌اش داخل مجموعه است.

**نثر پاسخ مدل همراه با شاهدهای اعتبارسنجی‌شده نمایش داده می‌شود.** `GenerationResult.answer` فقط وقتی سروشده می‌شود که دست‌کم یک claim از نظر quote و منبع معتبر باشد؛ منابع زیر پاسخ می‌آیند و نقل‌قول‌های تأییدشده در جزئیات بسته می‌مانند. امتناع مدل با جمله‌های ثابت سمت سرور حفظ می‌شود. این اعتبارسنجی وجود متن استنادی را ثابت می‌کند، نه اینکه تمام نثر پاسخ از آن نتیجه شود؛ ارزیابی وفاداری معنایی به بازبینی انسانی نیاز دارد.

**تاریخچهٔ چت فقط زمینهٔ موقت است.** رابط تاریخچه را در حافظهٔ همان صفحه نگه می‌دارد و حداکثر پنج نوبت قبلی را با پرسش، پاسخ و دستگیره‌های منبع می‌فرستد. API هر منبع را پیش از هر تلاش مدل زیر نقش و revision جاری دوباره می‌خواند؛ نوبتی که منبعش دیگر مجاز یا جاری نیست به مدل فرستاده نمی‌شود. تاریخچه در پایگاه‌داده یا نشست بعدی ذخیره نمی‌شود.

**تطبیق نقل‌قول تحمل نگاشت دارد ولی متن سروشده عیناً از سند است.** دلیل، اندازه‌گیری است نه سلیقه: در corpus خودِ پروژه ۸۷ از ۱۰۹ قطعه نیم‌فاصله دارند (۴۵۹ بار در ۳۳۲۶۲ نویسه، حدود ۱٫۴٪ نویسه‌ها)، پس یک نقل‌قول ۱۰۰ نویسه‌ای با احتمال ~۷۵٪ دست‌کم یک نیم‌فاصله دارد و آزمون لفظی خالص حدود سه‌چهارم نقل‌قول‌های معتبر را رد می‌کرد. نگاشت فقط برای **مقایسه** به‌کار می‌رود؛ `find_quote` بازه‌ای از متن passage را برمی‌گرداند و همین بازه سروشده می‌شود، پس آنچه کاربر می‌بیند همیشه متنی است که سند واقعاً دارد — حتی وقتی مدل فقط پس از نرمال‌سازی با سند توافق داشته باشد. `CODE_STYLE.md` بخش ۶ همین را می‌خواهد: کد نرمال‌سازی جست‌وجو نباید متن مرجع را بازنویسی کند.

**دو قاعده نقل‌قول را محدود می‌کنند.** **پیوستگی:** نقل‌قول باید دنبالهٔ توکن‌های مجاور باشد؛ دو تکهٔ واقعی از یک قطعه که به هم چسبیده‌اند از هیچ چیزی نقل نمی‌کنند، و پذیرفتنشان استنادی را گواهی می‌کرد که هیچ جمله‌ای در سند پشتیبانی نمی‌کند. **کف توکن:** یک واژه به‌تنهایی نقل‌قول نیست؛ کف دو توکن است نه شمار نویسه، چون واژه‌های فارسی کوتاه‌اند و کف نویسه‌ای که «مهلت» را کنار بگذارد، عبارت‌های کوتاه واقعی را هم کنار می‌گذارد.

**نقل‌قول تأییدشده grounding را اثبات می‌کند، نه وفاداری جمله را.** یعنی ثابت می‌کند ادعا به متنی تکیه دارد که واقعاً در سند مجاز هست؛ ثابت نمی‌کند جمله نتیجهٔ درستی از آن متن است. ملاک «پشتیبانی استناد» در `evaluation-guide.md` داوری انسانی است و در پارت ۱۸ سنجیده می‌شود. ادعای بیش از این دربارهٔ قابلیت اطمینان مدل در این کد وجود ندارد.

**دروازهٔ نهایی پیش از تحویل، دوباره اجرا می‌شود.** پنجرهٔ بین ارسال به provider و تحویل واقعی است و چند ثانیه طول می‌کشد. باریک‌سازی نقش، حذف یا جایگزینی revision که در آن پنجره بنشیند نباید پاسخ قدیمی را تحویل دهد، پس `answer` قطعه‌های ارجاع‌شده را یک‌بار دیگر زیر allowlist در نشست تازه می‌خواند. ترتیب عمدی است: **دروازه پیش از اعتبارسنجی می‌آید**، پس نقل‌قول فقط مقابل متنی سنجیده می‌شود که در آخرین لحظه مجاز بوده و اثبات هویت متن جداگانه لازم نمی‌شود. بازخوانی هم یک پرسش را بی‌پاسخ می‌گذارد: `read_ranked_chunks` شرط `revision = current_revision` را می‌خواهد، پس جایگزینی ردیف‌های قدیمی را ناپدید می‌کند و متن تازه زیر رتبه‌بندی قدیمی هرگز برنمی‌گردد.

**سقف پنج منبع در خودِ نوع اعمال می‌شود، نه در برش.** `AnswerConfig.__post_init__` مقدار `max_sources` را به بازهٔ `۱..MAX_SOURCES` محدود می‌کند و **بلاک‌کننده (raise) می‌کند، نه برش**. دو دلیل: اول اینکه تنها نقطهٔ ورود یک مقدار بد همین است — هر مسیر ساخت، `dataclasses.replace` هم، این را اجرا می‌کند — پس هیچ فراخوانندهٔ کنونی یا آینده نمی‌تواند از آن رد شود. دوم اینکه این عدد حدّ چند متن سند به بیرون می‌رود، پس خطا باید آشکار شود؛ سروکردنِ خاموش به پنج به‌جای شش، فراخواننده را در این باور نگه می‌داشت که شش خواسته است. نکته‌ای که یافتهٔ بازبینی آشکار کرد و از خودِ شرح فراتر بود: **مقدار منفی فقط «زیادی نمی‌فرستاد» نبود، `hits[:-6]` یعنی «همه به‌جز شش آخر»** — یعنی پیکربندی اشتباه بی‌صدا **کدام** شواهد به مدل می‌رسید را عوض می‌کرد و دقیقاً همان‌هایی را که پاسخ می‌دادند حذف می‌کرد. صفر هم رد می‌شود، چون هر فراخوانی را به امتناع تبدیل می‌کند در حالی که سقفی پیکربندی‌شده گزارش می‌دهد.

**لغو دسترسی از دستگیرهٔ جعلی تفکیک شده است.** `EVIDENCE_REVOKED` یعنی سندی که واقعاً ارجاع داده شده دسترسی‌اش را از دست داده؛ `UNKNOWN_EVIDENCE_ID` یعنی مدل دستگیره‌ای ساخته که هرگز فرستاده نشده. گفتن «سند بسته شد» دربارهٔ دستگیرهٔ جعلی، اپراتور را به لاگ کنترل دسترسی می‌فرستد در حالی که باید دنبال prompt و بازیابی بگردد.

**پاسخ برای اولین بار شامل متن سند است، و همین‌جاست که مرز جابه‌جا می‌شود.** پارت‌های ۱۱ تا ۱۴ عمداً هیچ متنی چاپ نمی‌کردند، چون خروجی گزارش به ترمینال، تیکت و گزارش اشکال می‌رسد و `quote` هر claim خودِ سند است. در `POST /api/answers` متن **در پاسخ** عبور می‌کند و **هرگز در لاگ، برچسب متریک یا پیام خطا**. دو مسیر شکست جدا آزموده شده‌اند — رد ارائه‌دهنده و citation نامعتبر — چون handler خطا آسان‌ترین جای یک کد برای نشت همان محتوایی است که قاعدهٔ لاگ دربارهٔ آن است. آنچه در لاگ می‌رود: `request_id`، نقش، شمارش claim و منبع، flagهای امتناع، مدت، و برای شکست **دلیل ساختاریافته**؛ نه سؤال، نه پاسخ، نه نقل‌قول، نه شناسهٔ سند.

**سه پاسخِ منفیِ یکسان، نه یک پاسخِ منفیِ کلی.** `GET /api/sources/...` سه راه برای رد دارد — سند نیست، سند اجازه ندارد، revision کهنه است — و هر سه **یک status و یک بدنِ یکسان** می‌دهند. یک query این‌ها را با هم حمل می‌کند، پس نه store می‌تواند تشخیص دهد و نه route شاخه‌ای دارد که بتواند از آن فرق بگیرد. متن `not found` بار است و نه تزئین: تنها رشته‌ای است که برای هر سه صادق است، و بدنه‌ای مثل «forbidden» به کارمند می‌گفت سند مدیریتی وجود دارد — یعنی همان نشتی که این endpoint برای بستنش ساخته شده. آزمون این خاصیت را بین خودِ سه پاسخ مقایسه می‌کند، نه با یک کد ۴۰۴؛ آزمونی که فقط «۴۰۴» را بسنجد با بدن‌های متفاوت هم پاس می‌شود.

**خطای پایگاه‌داده نباید خود را «پیدا نشد» جا بزند.** بلعیدن استثنا در `read_source_section` وسوسه‌انگیزتر شکل همان نقص است، چون *شبیه* ایمنی بیشتر به نظر می‌رسد: ۴۰۴ به‌جای ۵۰۰. کاری که می‌کند این است که یک query شکسته یا اتصال قطع‌شده را با «این سند وجود ندارد» یکی می‌گیرد و اپراتور را دنبال مسئلهٔ مجوزی می‌فرستد که نیست. store منتشر می‌کند؛ تصمیم دربارهٔ گفتنش به route است و فقط برای خطاهایی که route واقعاً می‌شناسد.

**سقف پنجاه درخواست روزانه با محدودسازی نقش‌محور محافظت نمی‌شود.** محدودسازی `POST /api/answers` فقط جلوی حلقهٔ بی‌پایان و ارسال دوباره را می‌گیرد؛ کاربری که دو بار در ساعت بپرسد سهمیه را تمام می‌کند. محافظت از آن یعنی بودجهٔ روزانه، و آن تصمیم محصولی است دربارهٔ اینکه کاربر در روز چند سؤال بپرسد، پس عددی برایش ساخته نشده.
**مدل تولید هیچ شناسهٔ سندی نمی‌بیند.** شواهد با یک دستگیرهٔ بی‌معنا (`E1`, `E2`) فرستاده می‌شوند، نه `document_id`/`section_id`/`revision`. مدل نمی‌تواند سندی را نام ببرد که مجاز به خواندنش نبوده، چون اصلاً آن را نمی‌بیند؛ تطبیق دستگیره با `SourceRef` بعد از **بازبینی دوبارهٔ مجوز** در پارت ۱۴ انجام می‌شود. تنها بررسی‌ای که adapter می‌تواند انجام دهد این است که دستگیرهٔ ارجاع‌شده همان‌هایی باشد که فرستاده؛ اینکه نقل‌قول واقعاً در همان قطعه هست یا نه پرسشی دربارهٔ corpus است و کار پارت ۱۴ است.

**structured output یک تضمین است، نه یک درخواست — تا وقتی routing آن را اجباری کند.** `response_format` به‌تنهایی درخواست است: طبق مستندات رسمی OpenRouter پارامتری که endpoint پشتیبانی نکند **نادیده گرفته می‌شود**، نه اینکه رد شود. آن‌وقت متن آزادِ روان برمی‌گردد و شکست شبیه «نقض طرح‌واره» به نظر می‌رسد در حالی که در واقع یک downgrade خاموش است. به همین دلیل درخواست `provider.require_parameters: true` می‌فرستد که endpoint ناسازگار را کنار می‌گذارد به‌جای اینکه پارامتر را دور بیندازد. همان تنظیم باعث می‌شود **فهرست پارامترها یک موضوع درستی باشد**: هر کلید اضافه یک راه دیگر برای غیرقابل‌مسیریابی‌شدن یک endpoint سالم است. تصمیم Part 13 برای نفرستادن `temperature` تاریخی است؛ Part 21 آن را به پارامتر تنظیم‌شدهٔ per-connection برای chat تبدیل کرد. اگر endpoint آن را نپذیرد، درخواست نباید بی‌صدا بدون آن ادامه یابد.

**تلاش دوم متنِ پس‌گرفته‌شده را دوباره نمی‌فرستد و repair سقف را دو برابر نمی‌کند.** دو تلاش و سی ثانیه برای هر تلاش، **مشترک** بین retry شبکه و یک repair؛ اگر repair بودجهٔ تازه‌ای می‌خواست، بودجه پنهان دو برابر می‌شد. بدنهٔ هر تلاش از نو ساخته می‌شود و متن قبلی مدل عمداً بازفرستاده نمی‌شود، چون همان متن فقط توکن اضافه مصرف می‌کند. یک خطای دائمی retry نمی‌شود: `403` یا `401` با هر تعداد تلاش همان‌طور شکست می‌خورد و `catch-all` هم وجود ندارد، چون تبدیل یک باگ ناشناخته به «provider در دسترس نیست» یعنی خرابی بی‌صدا.

**`200` هم موفقیت نیست.** طبق مرجع خطا، درخواست غیرجریانی می‌تواند `200 OK` بگیرد که بدنه‌اش فقط یک شیء `error` است و `choices` ندارد؛ و `finish_reason` می‌تواند `error`، `length` یا `content_filter` باشد. خواندن `choices[0]` اول یعنی `IndexError` نوع‌ناشناس روی خرابی provider. طبقه‌بندی روی `error.metadata.error_type` انجام می‌شود نه وضعیت HTTP، چون وضعیت در این حالت همیشه `200` است و `error.code` ۵۰۲ با `provider_unavailable` می‌آید — که روی endpoint رایگان واقعی و حدوداً یک تماس در هشت رخ می‌دهد. `finish_reason: "length"` عمداً retry نمی‌شود: راه‌حل مستندشده بالا بردن سقف توکن است، نه پرسیدن دوباره.

**ادعای نامعتبر در خروجی مدل، خودِ خطاست.** دستگیرهٔ ناشناخته رد می‌شود، چون مدل دارد استنادی می‌سازد که هرگز فرستاده نشده. هر claim باید هر سه میدانش رشته باشد؛ claim ناقص نگه داشته نمی‌شود، چون claimی که نقل‌قول ندارد از نظر پارت ۱۴ با claimی که نقل‌قولش در متن نیست قابل تفکیک نیست. دلیل امتناع یک مجموعهٔ بسته است و مقدار ناشناخته رد می‌شود، و مقادیر تکراری به یک مجموعه فرو کاسته می‌شوند (در یک اجرای واقعی چهار بار تکرار شده بود و متن مرکبِ نهایی همان جمله را چهار بار تکرار می‌کرد).

**تنها `index` نگاشت می‌شود، نه متن.** پاسخ provider سند را echo می‌کند و اگر مرجع نگاشت بود، مدلی که متن را بازنویسی کند تعیین می‌کرد نمرهٔ کدام chunk است. `index` با `type(value) is int` بررسی می‌شود نه `isinstance`، چون JSON `true` در پایتون `bool` است و `bool` زیرکلاس `int`؛ با `isinstance` مقدار `true` به‌عنوان index شمارهٔ ۱ پذیرفته می‌شد و نمرهٔ واقعی به chunk اشتباه می‌چسبید. بازه و یکتایی هم دفاعی‌اند: schema منتشرشده برای `index` حدی اعلام نکرده است. خروجی نامعتبر، کم یا اضافه، یا نمرهٔ نامتناهی رد می‌شود و fallback خاموش ندارد.

**گزارش و preflight هیچ متنی چاپ نمی‌کنند.** نه پرسش، نه متن قطعه، نه عنوان، و نه حتی `repr` یک `RerankCandidate` — چون `repr` در traceback و پیام شکست آزمون ظاهر می‌شود. خطای provider با پیام ثابت و نام کلاس استثنا گزارش می‌شود، چون پیام adapter می‌تواند بدنهٔ پاسخ gateway را نقل کند و آن بدنه ورودی را بازتاب می‌دهد.

**مسیر خطای گزارش هم متن نمی‌دهد.** `EmbeddingProviderError` به‌صراحت گرفته می‌شود و فقط یک پیام ثابت به‌همراه نام کلاس استثنا چاپ می‌شود. پیام adapter می‌تواند تا ۲۰۰ نویسه از بدنهٔ پاسخ Ollama را داشته باشد و Ollama ورودی ردشده را بازتاب می‌دهد — که اینجا همان پرسش است. `catch-all` هم وجود ندارد: خطای ناشناخته باید traceback خودش را نگه دارد، چون تبدیل هر باگ آینده به «provider در دسترس نیست» یعنی خرابی بی‌صدا.

**همین قاعده در مسیر HTTP، پس از بازبینی پارت ۱۵.** بند بالا CLI را پوشش می‌داد و API بیرون مانده بود: `answers.py` فقط خطای generation و `InvalidGeneration` را می‌گرفت، در حالی که retrieval هم سؤال را از همان adapter محلی embed می‌کند. یک خطای Ollama از این مسیر به handler عمومی می‌رسید و **پرسش کاربر به traceback و log می‌رفت** — همان چیزی که بخش ۷ و قاعدهٔ `CODE_STYLE.md` بند ۹ منع می‌کنند. `EmbeddingProviderError`، `IndexProvenanceMismatchError` و `RetrievalDomainTooLargeError` اکنون به ۵۰۲ با پیام ثابت نگاشت می‌شوند و فقط نام کلاس در log ثبت می‌شود. گرفتن **باریک** است عمداً: نوع‌های خطای provider، نه `Exception`. یک `catch-all` هر باگ واقعی را هم به ۵۰۲ تخت تبدیل می‌کرد، و handlerای که همه‌چیز را پنهان می‌کند همان چیزی است که یک نقص واقعی را از یک انتشار زنده بیرون می‌برد. آزمون `test_a_genuine_bug_is_not_flattened_into_a_generic_502` همین را نگه می‌دارد.

**کلاینت embedding قابل‌بستن است، پس هر سؤال یک pool ندارد.** `build_provider` یک `httpx.AsyncClient` می‌ساخت و providerی برمی‌گرداند که آن را نگه داشته بود، ولی adapter `aclose` نداشت و `finally` مسیر فقط کلاینت generation را می‌بست. worker مشکلی ندارد چون فرایندی یک‌بارمصرف است؛ مسیر پاسخ یکی را **به ازای هر سؤال** می‌ساخت، پس هر سؤال یک connection pool برای عمر فرایند رها می‌کرد. اکنون فراخواننده کلاینت را می‌دهد و همان کلاینتی است که `finally` می‌بندد، پس نشت با ساختار بسته می‌شود نه با یک چرخهٔ عمر تازه که باید به یاد بماند. اولین تلاشم provider ماندگار روی `app.state` بود و به یک `close_vector_providers` و قلاب خاموشی نیاز داشت؛ آن راه در docstring رد شد چون یک handshake به Ollama محلی بهای یک cache حالت‌دار با چرخهٔ عمر جدا نیست.

**یادداشت تاریخی پارت ۱۵ دربارهٔ `RERANK_ENABLED`:** مسیر پاسخ در آن نسخه یک `RetrievalConfig()` خالی می‌فرستاد که پیش‌فرضش `rerank_enabled=False` است، و هیچ providerی rerank نمی‌داد. یعنی تنظیم وجود داشت، worker آن را می‌خواند، و روی تنها مسیری که یک کاربر طی می‌کند بی‌اثر بود: استقراری با `RERANK_ENABLED=true` پاسخ rerank‌نشده سرو می‌کرد و چیزی هم خراب به نظر نمی‌رسید. در اصلاح همان پارت، هر دو شاخه از آن تنظیم ساخته می‌شدند و تنها شاخهٔ فعال provider می‌ساخت؛ rerank خاموش **صفر** کار provider انجام می‌داد. این رفتار و پیکربندی env مربوط به نسخهٔ پیش از پارت ۲۰ است. اکنون تنظیم rerank از زنجیرهٔ DB می‌آید و خاموش‌بودن پیش‌فرض و نبود fallback برای خطاهای غیرقابل‌fallback پابرجاست.

**یادداشت تاریخی پارت ۱۵ دربارهٔ مرز خطای rerank:** تا پیش از آن اصلاح، نگاشت فقط خطاهای generation و embedding را پوشش می‌داد. تا وقتی rerank خاموش بود این نقص پنهان بود، اما همین که `RERANK_ENABLED=true` واقعاً provider را ساخت، دو راه نشت باز شد. **راه اول آشکار بود:** یک وضعیت غیرقابل‌retry از upstream، تا ۲۰۰ نویسه از بدنهٔ خودش را در پیام `RerankProviderError` نگه می‌دارد — و آن درخواست **متن سندِ مجاز** را حمل می‌کند، پس gatewayای که آن را بازتاب دهد یک passage را به traceback و log می‌برد. **راه دوم کمتر دیده می‌شد:** `build_rerank_provider` کلید خالی را **هنگام ساخت** رد می‌کند، یعنی درون `try` مسیر و پیش از خواندن هر پرسشی؛ پس استقراری با rerank روشن و بدون کلید، ۵۰۰ با traceback به کاربری می‌داد که سؤال پرسیده بود. در نسخهٔ همان پارت، هر دو به ۵۰۲ با پیام ثابت نگاشت شدند و فقط نام نوع در log ثبت می‌شد. در پارت ۲۰، انتخاب و فعال‌بودن زنجیره از DB می‌آید؛ رفتار خطاهای fallback در بند جاری پارت ۲۰ تعریف شده است. مسیر گذرا از قبل امن بود و عمداً همان‌گونه ماند: `arun_with_retry` پیام ثابت خودش را دوباره بالا می‌فرستد و adapter آن را به پیامی تبدیل می‌کند که فقط شمارش تلاش را نام می‌برد. یک آزمون تازه هم نگه می‌دارد که **خطای برنامه‌نویسی عمومی همچنان با traceback بیرون بیاید**؛ بدون آن، گشادن این catch به `Exception` هنوز همهٔ آزمون‌های دیگر را سبز نگه می‌داشت، چون همه خطای واقعی provider می‌دهند.

## 3. اسرار

- کلیدها، گذرواژه‌ها و کوکی‌های واقعی را در کد، مستندات، log، خروجی ابزار یا Git قرار ندهید.
- طبق قرارداد پارت ۲۰، کلیدهای provider در DB و با Fernet رمز می‌شوند؛ کلید رمزگذاری `APP_ENCRYPTION_KEY` در محیط خصوصی اجرا نگهداری شود. تنظیمات provider از env import نمی‌شوند. نام متغیرهای provider که در سوابق بخش‌های بعد آمده‌اند، وضعیت تاریخی همان پارت‌ها هستند؛ فایل محیطی محلی commit نشود.
- Compose، Ollama، tokenizer یا مدل Nomic را همراه imageها نصب نمی‌کند. مدیر provider embedding و مدل را از OpenAI، OpenRouter یا Ollama انتخاب می‌کند؛ برای provider ابری، متن chunkها هنگام ایجاد/بازسازی embedding از میزبان خارج می‌شود و ممکن است هزینه داشته باشد. برای تغییر فضای برداری موجود، UI پیش از شروع، شمار سندها و قطعه‌ها و هشدار egress/هزینه را نشان می‌دهد و تأیید صریح لازم است. در زمان بازسازی، عمل مستقل محدودکردن دسترسی سند به مدیران فوری است و برای نسخهٔ در انتظار نیز حفظ می‌شود.
- Rerank اختیاری و خاموش پیش‌فرض است. زنجیرهٔ انتخابی DB کلید خودش را دارد؛ محدودیت حریم خصوصی سرویس رایگان NVIDIA در صورت انتخاب آن پابرجاست: فقط corpus ساختگیِ غیرشخصی و غیرمحرمانه تا بازبینی حریم خصوصی ارسال شود.

## 4. متغیرهای محیطی

**تنظیمات محیطی فعلی:** `APP_ENCRYPTION_KEY`، تنظیم اتصال DB (`DB_HOST`، `DB_PORT`، `DB_NAME`، `DB_USER`) و تنظیمات استقرار غیرمرتبط با provider. نام‌های provider قدیمی در `.env.example` یا fixtureها پیکربندی runtime نیستند و provider manager از آن‌ها fallback نمی‌کند.

**خصوصی:** کلیدهای provider در DB رمز شده‌اند؛ `APP_ENCRYPTION_KEY` و `DB_PASSWORD` secret هستند. گذرواژهٔ حساب از فرم احراز هویت دریافت می‌شود و نباید در log یا مستندات ذخیره شود. `.env.example` در ریشه برای نام متغیرها و راه‌اندازی است؛ مقدارها یا وضعیت credentialهای محلی را از روی آن حدس نزنید. `.env` محلی باید خارج از Git بماند. مقدارها را هنگام ساخت connection string یا خطا log نکنید.

### قرارداد امنیت provider پارت ۲۰ — منتشرشده در ۲۰۲۶-۱۰-۱۳

کلیدهای provider در `/manager/providers` وارد و با Fernet در DB رمز می‌شوند؛ `APP_ENCRYPTION_KEY` برای رمزگذاری و بازیابی API keyها لازم است؛ اتصال Ollama بدون API key به آن نیاز ندارد. کلید باید جدا از DB در محیط خصوصی استقرار نگهداری شود و تا زمان بازرمزگذاری API keyهای ذخیره‌شده با کلید تازه ثابت بماند. نصب تازه provider ندارد و متغیرهای provider خودکار از env وارد نمی‌شوند. URL در هر تلاش اعتبارسنجی می‌شود: loopback و HTTPS عمومی مجازند؛ private LAN، metadata endpoint، redirect و DNSی که به نشانی ممنوع resolve شود رد می‌شود. این موارد `ProviderConfigurationError` و terminal هستند، پس به retry یا اتصال بعدی نمی‌روند. Fallback برای chat و rerank فقط در خطاهای مجاز همان زنجیره است؛ embedding بین مدل‌های متفاوت fallback نمی‌کند. مجوز، evidence، citation یا digest نامعتبر زنجیره را متوقف می‌کند و gate شواهد پیش از هر تلاش تازه اجرا می‌شود. refusalهای سیاستی provider مانند `finish_reason=content_filter` یا `message.refusal` نیز terminal هستند و fallback نمی‌شوند. پذیرش embedding چندمدلی در [گزارش آزمون](TESTING.md) آمده است.

## 5. امنیت API

- ورودی پرسش، فایل و فراداده سمت سرور اعتبارسنجی شود؛ پسوند فایل به‌تنهایی اثبات نوع محتوا نیست.
- درخواست‌های تغییردهنده، از جمله login، ابتدا باید Origin منطبق داشته باشند؛ Origin غایب یا نامنطبق پیش از محدودکننده رد می‌شود. پس از آن یک limiter مشترک در هر نمونهٔ app با پنجرهٔ لغزان ۶۰ثانیه‌ای، حداکثر ۵ تلاش برای هر جفت IP/شناسه و ۳۰ تلاش برای هر IP اعمال می‌کند. حدود با `LOGIN_RATE_PAIR_LIMIT=5`، `LOGIN_RATE_IP_LIMIT=30` و `LOGIN_RATE_WINDOW_SECONDS=60` تنظیم می‌شوند. ورود ناموفق در هر دو سهم شمارش می‌شود؛ تلاش ردشده به علت سقف جفت نیز تا پرشدن سهم IP از بودجهٔ IP مصرف می‌کند. کلیدهای نگهداری‌شده به `LOGIN_RATE_MAX_KEYS=10000` محدودند؛ در ظرفیت کامل درخواست fail-closed و با 429 و `Retry-After` رد می‌شود. محدودیت ۱۰ درخواست پاسخ در دقیقه برای هر کاربر هنوز به پارت ۱۵ موکول است.
- کلید IP از آدرس peer واقعی اتصال گرفته می‌شود؛ هدرهای `Forwarded` و `X-Forwarded-*` مبنای اعتماد نیستند و Uvicorn باید با `proxy_headers=False` اجرا شود. برای اجرای مستقیم Uvicorn بیرون از `python -m app` نیز `--no-proxy-headers` را صریحاً بدهید. محدودیت شناخته‌شده: در اجرای فعلی API محلی، همهٔ peerها loopback هستند و پشت پراکسی محلی در سهم IP مشترک جمع می‌شوند؛ محدودسازی IPهای کلاینت به forwarding صریح و محدود به پراکسی‌های مورد اعتماد نیاز دارد و هنوز پیاده نشده است.
- مقادیر محدودسازی از environment هنگام ساخت app خوانده می‌شوند؛ پس از تغییر تنظیم‌ها، فرایند API را restart کنید.
- Argon2 در مسیر async مستقیم اجرا نمی‌شود؛ کار هش به ظرفیت thread محدود (۴ کار هم‌زمان) سپرده می‌شود تا تعداد کارهای محاسباتی محدود بماند.
- CORS فقط به مبدأهای لازم محدود شود؛ در معماری پیشنهادی، مرورگر از پراکسی same-origin استفاده می‌کند.
- شناسهٔ نقش، سطح دسترسی سند و مجوز API هرگز از ادعای کاربر پذیرفته نشوند.
- خطاهای API نباید query، سند غیرمجاز، stack trace یا secret افشا کنند. منبع غیرموجود و غیرمجاز یک پاسخ عمومی 404 دارند؛ فهرست و شمار فقط از اسناد مجاز ساخته شود. رندر Markdown باید HTML خام را غیرفعال یا sanitize کند و URLهای javascript/اجرایی را نپذیرد.

## 6. حفاظت از داده

- corpus این مخزن ساختگی است؛ دادهٔ واقعی کارکنان، رمز یا کلید وارد نکنید.
- اتصال پروژه به نمونهٔ موجود PostgreSQL 16 با نام `rag-postgres` از host port `5433` و پایگاه جداگانهٔ `enterprise_knowledge_copilot` انجام می‌شود. در ۲۰۲۶-۱۰-۰۴ پایگاه‌های `enterprise_knowledge_copilot` و `enterprise_knowledge_copilot_test` با حساب محدود `enterprise_knowledge_copilot` ساخته شد و schema با migration `0001` اجرا شد. این حساب superuser، `CREATEDB` یا `CREATEROLE` ندارد و فقط مالک همین دو پایگاه است.
- از حذف، بازسازی، تغییر پیکربندی یا پاک‌سازی container/volume و داده‌های قدیمی `rag-postgres` خودداری کنید. هر عملیات فقط باید پایگاه اختصاصی پروژه را هدف بگیرد.
- ساخت پایگاه‌ها و حساب محدود یک اقدام superuser و جدا از runtime برنامه است: اسکریپت idempotent `apps/api/sql/provision.sql` فقط objectهای جدید محدود به این پروژه می‌سازد و رمز از بیرون از مخزن و از راه متغیر محیطی `EKC_DB_PASSWORD` داخل container به `psql` می‌رسد؛ این روش عمداً به‌جای `-v` یا `-e` انتخاب شد چون هر دو مقدار را در argv فرایند آشکار می‌کنند. بررسی مالکیت و مجوز پیش از هر تغییری اجرا می‌شود و برخورد با کد خروج غیرصفر و بدون تغییر متوقف می‌شود. افزونهٔ `vector` عمداً بخشی از migration نیست و همین اسکریپت آن را می‌سازد، چون حساب کاربرد مجوز ساخت افزونه را ندارد.
- محدودیت شناخته‌شده: مجوز CONNECT در سطح connection قابل بستن نیست، چون سرویس `rag-postgres` موجود به‌صورت پیش‌فرض به `PUBLIC` دسترسی می‌دهد و لغو آن به‌معنای تغییر پایگاه‌های قدیمی و ممنوع است. مرز مجوز در لایهٔ application و با allowlist نام پایگاه‌داده در `apps/api/app/db/url.py` اعمال می‌شود؛ سخت‌سازی مجوزهای `rag_support` تصمیمی جداگانه و خارج از محدودهٔ این پروژه است.
- پیش از استفادهٔ واقعی، سیاست retention، backup و پاک‌سازی فیزیکی مشخص شود. log عادی متن خام پرسش، پاسخ، prompt یا سند را ذخیره نکند.

رمزها با Argon2id و نشست‌ها به‌صورت hash ذخیره می‌شوند. اجرای محلی HTTP فقط روی loopback؛ انتشار عمومی نیازمند HTTPS است. پاک‌سازی فیزیکی/backup و مدت retention قبل از ورود دادهٔ واقعی تعیین شوند؛ حذف منطقی بلافاصله بازیابی و نمایش منبع را قطع کند. فقط زمینهٔ مجاز به OpenRouter ارسال می‌شود؛ دادهٔ ارسال‌شده را recheck بعدی نمی‌تواند پس بگیرد. endpoint رایگان rerank داده‌ها را برای امنیت و بهبود محصول ثبت می‌کند؛ ارسال اطلاعات شخصی یا محرمانه ممنوع است. استفاده از دادهٔ واقعی در آینده نیازمند بازبینی حریم خصوصی/شرایط ارائه‌دهنده است.

## 7. ثبت رویدادها

- گذرواژه، API key، token نشست و محتوای حساس را ثبت نکنید.
- در صورت پیاده‌سازی، شناسهٔ اجرا، زمان، وضعیت، نسخهٔ مدل و شناسه/رتبهٔ منابع مجاز برای عیب‌یابی کافی است.
- خطاهای provider را پیش از ثبت از headerها، tokenها و payload حساس پاک کنید.

## 8. بارگذاری فایل

- فایل‌های `.md`، `.txt`، `.pdf`، `.docx`، `.xlsx` و `.xls` با سقف 1 MiB پذیرفته می‌شوند؛ متن نیز در مرورگر به فایل Markdown UTF-8 تبدیل می‌شود. اندازه و ساختار فایل پیش از staging و provider بررسی می‌شوند؛ فقط متن استخراج‌شده در DB قرار می‌گیرد و فایل خام نگهداری نمی‌شود. PDF باید لایهٔ متن داشته باشد؛ OCR، `.xlsm` و اجرای macro/فرمول پشتیبانی نمی‌شوند. PDF صفحه‌به‌صفحه، DOCX با ترتیب پاراگراف/جدول، و همهٔ شیت‌های Excel شامل شیت پنهان استخراج می‌شوند؛ Excel فقط مقدار ذخیره‌شده را می‌خواند. بسته‌های Office به 8 MiB دادهٔ بازشده و 4096 عضو، صفحه‌گسترده به 100000 سلول در هر شیت و PDF به 250 صفحه محدود است. چیدمان جدول/ستون PDF ممکن است در متن استخراجی دقیق نماند.
- بارگذاری و تعیین سطح دسترسی فقط برای مدیر است. سند با سطح دسترسی نامعلوم هرگز عمومی فرض نشود.
- متن فایل دادهٔ نامطمئن است، نه دستور؛ فایل نباید نقش یا سیاست دسترسی را تغییر دهد. پارت ۶ این قاعده را در کد enforce کرد: `parse_document` مقدار `access_role` داخل فایل را فقط به‌عنوان ادعای تأییدنشده برمی‌گرداند و `chunk_sections` نقش را از ورودی تأییدشدهٔ مدیر می‌گیرد؛ آزمون `test_a_file_claiming_manager_cannot_escalate_chunk_access` همین را ثابت می‌کند.
- پارت ۸ این قواعد را در کد enforce کرد: `app/api/manager.py` نقش را فقط از نشست سروری می‌خواند و پارامتری برای دریافت نقش از درخواست وجود ندارد؛ `Origin` پیش از هر عملیات بررسی می‌شود؛ پسوند، اندازه و UTF-8 پیش از هر نوشتن در DB بررسی می‌شوند؛ `access_role` فقط از `UploadInput` می‌آید و ادعای front matter نادیده گرفته می‌شود (آزمون `test_access_role_comes_from_metadata_not_the_file` یک فایل با ادعای `manager` را با سیاست `employee` بارگذاری می‌کند)؛ نقش ناشناخته به‌جای عمومی‌فرض کردن رد می‌شود؛ و سهمیهٔ قطعه پس از قطعه‌بندی و **پیش از** فراخوانی provider بررسی می‌شود تا برای سندی که جا نمی‌شود بردار پرداخت نشود.
- سند تازه تا پیش از `ready` هیچ `current_revision` ندارد، پس هیچ‌کس آن را بازیابی نمی‌کند؛ فعال‌سازی compare-and-swap دارد و شکست، `current_revision` قبلی را دست‌نخورده می‌گذارد. `safe_error` فقط یک کد ثابت است و متن سند یا پاسخ provider را نگه نمی‌دارد.
- **ایمنی lease، پس از سه نوبت بازبینی:** هر عملیات حساس به مالکیت سه شرط را می‌سنجد: `status = 'indexing'`، تطابق `lease_token`، و `lease_expires_at > clock_timestamp()`. دو تلهٔ زمانی اینجا وجود دارد و هر دو بسته شده‌اند. اول اینکه `now()` در PostgreSQL زمان **آغاز تراکنش** است و در طول انتظار روی قفل کهنه می‌شود، پس شرط زمانی روی `clock_timestamp()` (ساعت زندهٔ پایگاه‌داده) نوشته شده است. دوم اینکه شرطِ هر statement **پیش از** انتظارِ قفلِ آن ارزیابی می‌شود، پس ارزیابیِ پیش از انتظار به‌تنهایی کافی نیست. به همین دلیل فعال‌سازی سه قفل را به‌ترتیب می‌گیرد — قفل مشورتی ناشر، سپس ردیف job، سپس ردیف `documents` — و انقضای lease **پس از هر انتظار و درست پیش از نخستین تغییر**، یعنی پیش از جابه‌جایی `current_revision` و پیش از `ready`، دوباره با ساعت زنده سنجیده می‌شود. ردیف job در تمام این مدت `FOR UPDATE` قفل است، پس وضعیت و توکن نمی‌توانند زیر پایمان عوض شوند و فقط ساعت حرکت می‌کند. `renew_lease` هم به همین دلیل یک `UPDATE ... WHERE` ساده نیست؛ ردیف را قفل می‌کند و پس از انتظار بررسی می‌کند، وگرنه تمدیدی که پشت قفل ردیف صف شده بود می‌توانست lease منقضی را زنده کند. نتیجه: تراکنشی که پشت هر سه نوع قفل تا پس از انقضای lease منتظر بماند، نه می‌نویسد، نه منتشر می‌کند و نه تمدید می‌شود؛ کل تراکنش rollback می‌شود، سند revision جاری خود را نگه می‌دارد و job `ready` نمی‌گردد. بررسی‌های دیگرِ بازبینی برقرار است: سهمیهٔ قطعه یک رزرو اتمیک داخل فعال‌سازی و زیر قفل مشورتیِ مشترک با همهٔ ناشرهاست؛ و بدنهٔ multipart پیش از پارس هم از نظر Origin و نقش و هم از نظر اندازه محدود می‌شود.
- **سقف بدنه در لایهٔ ASGI، و 413 در مسیر chunked، هر دو از بازبینی پارت ۱۵:** سقف روی مدل درخواست اعمال می‌شود نه روی بدنه. `AnswerRequest` بیش از ۲۰۰۰ نویسهٔ سؤال را رد می‌کند، ولی FastAPI کل JSON را **پیش از** اجرای هر dependency پارس می‌کند، پس آن عدد بعد از خواندن بدنه اعمال می‌شود. چون pydantic فیلد ناشناخته را نادیده می‌گیرد، یک سؤال معتبر کنار یک فیلد اضافیِ ۵۰ مگابایتی پذیرفته می‌شد، و فرستنده‌ای که اصلاً نشست نداشت هم پیش از رد شدن توسط هر dependency می‌توانست تخصیص حافظه ایجاد کند. `UploadGuard` حالا هر دو مسیر را با یک شمارندهٔ جریان پوشش می‌دهد — سقف multipart برای upload و **۶۴ KiB** برای JSON مسیر پاسخ، چون آنجا فایلی در کار نیست و عدد multipart سقفی می‌بود که هیچ بدنهٔ موجهی به آن نمی‌رسد. شمارش روی جریان است نه روی `Content-Length`، پس درخواست chunked بدون سرور طول هم همان‌قدر محدود می‌شود.
  - **این باگ از پارت ۸ باقی مانده بود و فقط پارت ۱۵ آن را آشکار کرد.** `BodyTooLargeError` یک `Exception` ساده بود، و parser بدنهٔ استارلِت هر استثنایی را که از `receive` بیرون بیاید می‌گیرد و با `400 "There was an error parsing the body"` جایگزین می‌کند. یعنی **سقف اعمال می‌شد ولی کد 413 نمی‌داد** — روی هر دو مسیر، شامل upload که از پارت ۸. این یعنی یک بدنهٔ بیش‌ازحد «بدنهٔ خراب» گزارش می‌شد: به کلاینت می‌گفت درخواستش را اصلاح کند نه اینکه کمتر بفرستد، و یک آپلود بیش‌ازحد از بایت‌های خراب تشخیص‌داده‌نشدنی می‌شد. این استثنا اکنون `HTTPException` با وضعیت ۴۱۳ است، که FastAPI دست‌نخورده بالا می‌فرستد. هر دو لایه می‌توانند پاسخ دهند و این عمدی است: `ExceptionMiddleware` درون middleware کاربر می‌نشیند، پس در یک درخواست واقعی پیش از `except` خودِ guard پاسخ می‌دهد، در حالی که handler خود guard برای اپ ASGI خام باقی مانده — و هر دو وضعیت و بدنهٔ ثابت یکسان می‌دهند، پس اینکه کدام پاسخ داده‌اند قابل مشاهده نیست. آزمون‌های `test_a_chunked_oversized_body_is_refused_too` در هر دو فایل این را می‌پوشند.
- فقط سند فعال، جاری و آماده وارد جست‌وجو شود؛ جایگزینی یا کاهش دسترسی باید دسترسی به نسخهٔ قبلی را مطابق قواعد طراحی کنترل کند.

### Ollama میزبان و خروجی provider در Docker Compose — پارت ۲۳

Compose اصلی هیچ Ollama یا مدل embedding اجرا نمی‌کند. اگر مدیر Ollama میزبان را انتخاب کند، استثنای مقصد فقط برای provider نوع `ollama` در `http://host.docker.internal:11434` است؛ در مسیر عادی مقصد باید از شبکهٔ مجاز Docker بررسی و به IP تأییدشده pin شود. فایل اختیاری `compose.ollama-linux.yaml` برای Linux Engine، فقط همین مقصد را از طریق سوکت Unix به relay شبکهٔ میزبان می‌فرستد؛ relay تنها به `127.0.0.1:11434` میزبان وصل می‌شود، در شروع امتیاز root را پس از آماده‌کردن volume کنار می‌گذارد و هیچ پورت TCP تازه‌ای منتشر نمی‌کند. سوکت فقط به API و worker mount می‌شود و نباید به کانتینر نامطمئن داده شود. این استثنا مجوز private LAN، loopback، metadata یا hostname/port دیگر نیست و redirect همچنان مسدود است. OpenAI و OpenRouter از endpointهای عمومی HTTPS استفاده می‌کنند و محتوای chunkهای مجاز را می‌گیرند؛ انتخاب آن‌ها مسئولیت egress و هزینهٔ provider را دارد. تغییر provider روی index موجود تا تأیید صریح reindex آغاز نمی‌شود و index قبلی تا cutover اتمی فعال می‌ماند. API و worker به‌صورت inbound پورت میزبان ندارند؛ وب روی `127.0.0.1:3000` و PostgreSQL روی پورت loopback قابل تنظیم منتشر می‌شوند. نقش برنامه superuser نیست و رمز bootstrap PostgreSQL فقط به سرویس DB داده می‌شود. راهنمای کاربر در [ollama-setup.md](../ollama-setup.md) است.

### ورود corpus و پنل مدیریت (پارت ۹)

CLI اپراتوری فقط با حساب فعال مدیر کار می‌کند و نقش هر یک از ۲۰ شناسه را از allowlist ثابت سمت سرور می‌گیرد؛ ادعای نقش در front matter پذیرفته نمی‌شود. پیش از هر نوشتن، کل corpus از نظر فایل‌های مورد انتظار، اندازه، UTF-8، metadata و section ID اعتبارسنجی می‌شود. ورود تکراری یکسان idempotent است؛ شناسهٔ موجود با متن یا سیاست متفاوت fail-closed رد می‌شود. صفحهٔ `/manager/documents` نقش را روی سرور بررسی می‌کند؛ proxy فقط GET فهرست/وضعیت و POST upload را با نشست معتبر عبور می‌دهد و پیش از خواندن body، Origin و نقش مدیر را بررسی می‌کند. سقف کل body هنگام stream برابر ۱ MiB + 64 KiB است؛ پاسخ proxy فقط فراداده و کد خطای امن را عبور می‌دهد.

### Proxy پرسش‌وپاسخ (پارت ۱۶)

`POST /api/answers` فقط Origin وب را می‌پذیرد و سقف ۶۴ KiB را حین خواندن stream اعمال می‌کند. مرز مجوز و allowlist سند در API باقی می‌ماند؛ صفحهٔ `/ask` صرفاً نشست را بررسی می‌کند. `npm audit --omit=dev` هیچ آسیب‌پذیری runtime نیافت. audit توسعه پنج رخداد high را برای **یک advisory** در `braces@3.0.3` گزارش کرد ([GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm))، از مسیر `eslint-config-next` → `@next/eslint-plugin-next` → `fast-glob` → `micromatch` → `braces`. ابزار `fast-glob` در این زنجیره فقط برای تنظیم ثابت lint است؛ پیکربندی فعلی `next.rootDir` سفارشی ندارد و ورودی درخواست به آن نمی‌رسد. advisory نسخهٔ اصلاح‌شده‌ای ندارد. پیگیری به به‌روزرسانی بعدی وابستگی‌ها یا 2026-10-17 موکول شده است؛ اثر باقی‌مانده در صورت الگوی پیکربندی مخرب، از کار افتادن فرایند lint است.

### فهرست اسناد و متن منبع (پارت ۱۷)

`GET /api/documents` و `GET /api/sources/{document_id}/sections/{section_id}?revision=...` از proxy هم‌مبدأ عبور می‌کنند و پاسخ‌ها `no-store` هستند. این proxyها صرفاً خواندن را عبور می‌دهند؛ API نشست و allowlist نقش را مرجع نهایی می‌داند. سه حالت منبع ناموجود، غیرمجاز و revision منسوخ در API پاسخ 404 یکسان و هم‌بایت دارند؛ رابط نیز یک پیام عمومی نشان می‌دهد. محتوای منبع به‌صورت plaintext رندر می‌شود و به‌عنوان HTML تفسیر نمی‌شود. فهرست، برچسب نقش دسترسی را فقط برای مدیر نشان می‌دهد.
