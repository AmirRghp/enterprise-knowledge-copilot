# شیوهٔ کدنویسی و قراردادها

## 1. اصول کلی

- کد خوانا و متمرکز بنویسید؛ abstraction و dependency تازه فقط با نیاز روشن.
- پیش از انتخاب الگو، ساختار موجود و سند فنی مرتبط را بخوانید. برای وضعیت جاری به [برنامهٔ اجرا](plans/plans.md) رجوع کنید.
- تغییر را به درخواست محدود کنید و قرارداد دسترسی، استناد و چرخهٔ عمر سند را حفظ کنید.

## 2. نام‌گذاری

- Python: تابع/متغیر `snake_case`، کلاس `PascalCase`، ثابت `UPPER_SNAKE_CASE`.
- TypeScript/React: کامپوننت و نوع `PascalCase`؛ تابع/متغیر `camelCase`.
- فایل‌ها و مسیر API از قرارداد چارچوب پیروی کنند؛ نام جدول/ستون پایگاه‌داده `snake_case` باشد.
- شناسه‌های قراردادی مانند `document_id` و `section_id` را در مرز API تغییر نام ندهید.

## 3. ساختار پوشه‌ها

- ساختار پیشنهادی در `docs/ARCHITECTURE.md` مرجع بحث است، نه الزام به ساخت آن در مرحلهٔ مستندسازی.
- رابط موجود Next.js در `apps/web/` و API ماژولار FastAPI در `apps/api/` قرار دارد؛ ماژول‌های دامنه از route و adapter ارائه‌دهنده جدا باشند.
- سندهای سازمان در محصول بارگذاری می‌شوند؛ مجموعهٔ ارزیابی توسعه در `eval/` و مستندات پروژه در `docs/` می‌مانند. `eval/` وارد image تولید نمی‌شود.

## 4. واردسازی‌ها

- واردسازی استفاده‌نشده و import چرخه‌ای نسازید.
- وابستگی ماژول‌ها یک‌طرفه باشد: route به service/domain وابسته باشد؛ domain به framework یا provider وابسته نشود.
- وابستگی providerها پشت interface کوچک و قابل جایگزینی بماند.

## 5. کامپوننت‌ها

- کامپوننت رابط مسئولیت محدود داشته باشد و قواعد RTL و دسترس‌پذیری رابط فارسی را رعایت کند.
- درخواست شبکه و دسترسی به داده را در UI تکرار نکنید؛ از مرزهای API موجود استفاده کنید.
- نقش و مجوز با پنهان‌کردن یک کنترل رابط اعمال نمی‌شود؛ backend مرجع مجوز است.

## 6. توابع

- هر تابع یک کار مشخص با ورودی/خروجی روشن انجام دهد.
- منطق دسترسی را در service سمت سرور نیز اجرا کنید، حتی اگر route قبلاً آن را بررسی کرده باشد.
- کد normalization جست‌وجو نباید متن مرجع نمایش/استناد را بازنویسی کند.

## 7. رسیدگی به خطا

- خطاها را در مرز مناسب تبدیل به پاسخ روشن و غیرحساس کنید؛ از بلعیدن خطا یا پاسخ سیاستی حدسی بپرهیزید.
- خروجی مدل را پیش از نمایش اعتبارسنجی کنید: هر ادعا باید به `document_id`/`section_id` مجاز متصل باشد و نقل‌قول با متن شاهد تطبیق کند.
- خطای نهایی provider یا پایان مهلت درخواست نباید به پاسخ بی‌پشتوانه تبدیل شود.

## 8. توضیحات در کد

- توضیح برای چرایی تصمیم، محدودیت غیرآشکار یا قرارداد مهم باشد.
- توضیحی که فقط خط بعدی را با کلمات دیگر می‌گوید حذف شود.
- تصمیم محصولی یا فرضیهٔ هنوز تأییدنشده را به‌عنوان واقعیت قطعی معرفی نکنید.

## 9. ثبت رویدادها

- Python از logging استاندارد با خروجی ساختاریافته و request_id استفاده کند؛ در Next logger سروری واحد و بدون payload حساس باشد. logger موازی اضافه نکنید.
- گذرواژه، کلید، token، متن خام پرسش/prompt/سند و محتوای غیرمجاز را ثبت نکنید.
- مصرف ثبت‌نشده را صفر گزارش نکنید؛ مقدار نامعلوم باید نامعلوم بماند.

## 10. قالب‌بندی

- API فعلی از Python 3.12 استفاده می‌کند؛ نسخه‌های وابستگی در `apps/api/uv.lock` قفل شده‌اند. Ruff برای lint/format و mypy strict برای بررسی نوع در `apps/api/pyproject.toml` تنظیم شده‌اند.
- فرمان‌های API را از `apps/api/` اجرا کنید: `uv run --locked ruff check .`، `uv run --locked ruff format --check .` و `uv run --locked mypy app`.
- رابط `apps/web/` از Next.js 16.3.8، React 19.3.0 و TypeScript 5.9.3 استفاده می‌کند؛ نسخه‌ها در `package-lock.json` قفل‌اند. ESLint، Prettier و `tsc --noEmit` با فرمان‌های `npm run lint`، `npm run format:check` و `npm run typecheck` اجرا می‌شوند.
- قلم فارسی رابط از فایل محلی Vazirmatn 33.003 با مجوز OFL و `next/font/local` بارگذاری می‌شود؛ متغیر `--font-vazirmatn` در استایل‌ها مصرف می‌شود. توکن‌های تم تیره از [نظام طراحی](DESIGN_SYSTEM.md) می‌آیند؛ اعداد فنی در صورت نیاز monospace سیستمی‌اند.
- قالب‌بندی خودکار فقط روی فایل‌های محدودهٔ تغییر اجرا شود.
- در TypeScript از typeهای صریح برای قرارداد API و در Python از annotation برای مرزهای service استفاده شود.

## 11. انجام دهید

- الگوهای موجود و قراردادهای `docs/` را دوباره به‌کار ببرید.
- تغییرات schema را با migration افزایشی و مستند همراه کنید.
- تغییر provider یا retrieval را با ثبت پیکربندی و ارزیابی نسخه‌دار همراه کنید.
- متن و شناسهٔ پایدار سند/بخش را برای استناد قابل ردیابی نگه دارید.

## 12. انجام ندهید

- مقصد native/Compose فقط از allowlist فعلی Settings و app/db/url.py بیاید؛ آزمون‌ها فقط enterprise_knowledge_copilot_test را هدف بگیرند. DB یا volume اضافی بدون دامنهٔ صریح نسازید.
- container یا دادهٔ قدیمی `rag-postgres` را حذف، بازسازی یا reset نکنید.
- secret، دادهٔ واقعی، یا سند مدیریتی را به client یا log نشت ندهید.
- بدون نیاز، dependency، abstraction، cache مشترک بین نقش‌ها یا worker/صف توزیع‌شده اضافه نکنید.
- فایل‌های بیرون از دامنهٔ کار را بی‌دلیل تغییر ندهید.
- برای تنظیمات API، فایل `.env` ریشه را با مسیر صریح بخوانید؛ مقادیر environment سیستم طبق اولویت Pydantic Settings بر فایل مقدم‌اند. مقادیر credential از نوع `SecretStr` هستند و خطای پیکربندی نباید مقدار ورودی را افشا کند. credentialهای خالی برای health به‌تنهایی مانع نیستند؛ اتصال DB و provider پیکربندی‌شده credential معتبر می‌خواهند و key provider از env وارد نمی‌شود.

## 13. قرارداد تغییرات برنامهٔ جدید

- مالک هر قرارداد در [نقشهٔ اسناد](AGENTS.md) معلوم است؛ README و roadmap خلاصه و لینک باشند، نه کپی schema و checklist plans.
- هر کارت شناسهٔ ثابت دارد. public type، caller، fixture، schema و UI تحت تأثیر پیش از edit مشخص شوند؛ نتیجهٔ هر کارت قابل استفاده و بازبینی باشد.
- مسیر source و binary staging از ورودی client ساخته نشود؛ storage key و alias معتبر از سرور بیاید. raw/text/search-normalized/page provenance نوع و نام مشخص داشته باشند.
- policy را در source connector یا SDK تکثیر نکنید؛ service مرکزی سمت سرور تصمیم بگیرد. normalization به quote اصلی دست نزند.
- handler/parsing/frontend sanitization و محدودیت ورودی با جابه‌جایی کد حفظ شوند. متد/response قدیمی بدون version/migration صریح شکسته نشود.
- فرمت/mimetype/runtime تازه پشت قرارداد کوچک موجود بماند؛ dependency جدید با evidence نیاز/مجوز/هزینه ثبت شود. LangChain، queue، database و wrapper اضافه از نقشهٔ راه استنتاج نمی‌شوند.
